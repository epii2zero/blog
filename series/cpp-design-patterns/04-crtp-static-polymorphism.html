CRTP와 정적 다형성 — 그리고 deducing this

가상 함수 없이 공통 동작을 물려주는 CRTP를 다룹니다. 믹스인 세 가지로 베이스가 파생 타입을 어디에 쓰는지 나누고, C++20 기본 비교와 C++23 deducing this가 대신하는 용도와 CRTP에 남는 용도를 예제로 확인합니다. 잘못된 상속을 막는 장치도 함께 봅니다.

가상 함수 없이 여러 타입에 공통 동작을 물려주려면 어떻게 해야 할까요? 그리고 C++23의 deducing this는 그 방법인 CRTP를 얼마나 대신할까요? 이 글은 CRTP를 "베이스가 파생 타입을 어디에 쓰는가"에 따라 세 용도로 나누고, 용도마다 현대 C++의 대안이 있는지 코드로 확인합니다. 다 읽고 나면 CRTP 코드를 볼 때 지워도 되는 것과 남겨야 하는 것을 구분할 수 있습니다.

문제 상황

센서 값을 다루는 프로그램에 Celsius, Pascal 같은 작은 값 타입이 여럿 있다고 해 봅시다. 값 하나에 8바이트 정수 하나가 들어 있고, 배열에 수백만 개씩 담깁니다. 이 타입들에 공통 동작을 붙이려고 합니다.

  • < 하나만 정의하면 >, <=, >=도 쓸 수 있어야 한다.
  • "21 °C", "101325 Pa"처럼 값과 단위를 이어 붙인 문자열을 만들 수 있어야 한다.
  • 테스트에서 누수를 찾기 위해, 살아 있는 객체 수를 타입별로 세어야 한다.
  • 공통 동작을 붙여도 객체가 커지면 안 된다. Celsius와 Pascal을 비교하는 코드는 컴파일되지 않아야 한다.

타입은 빌드할 때 모두 정해집니다. 실행 중에 종류를 바꾸거나 한 목록에 섞어 담을 일은 없습니다.

순진한 구현

공통 동작이라면 보통 기반 클래스를 떠올립니다. 요구 사항을 가상 함수와 정적 변수로 옮기면 다음과 같습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <string>

class Quantity {
 public:
  Quantity() { ++live; }
  Quantity(const Quantity&) { ++live; }
  Quantity& operator=(const Quantity&) = default;
  virtual ~Quantity() { --live; }

  std::string describe() const { return std::to_string(value()) + ' ' + unit(); }
  bool less_than(const Quantity& other) const { return value() < other.value(); }

  static inline int live = 0;

 private:
  virtual long long value() const = 0;
  virtual std::string unit() const = 0;
};

class Celsius final : public Quantity {
 public:
  explicit Celsius(long long v) : value_(v) {}

 private:
  long long value() const override { return value_; }
  std::string unit() const override { return "°C"; }
  long long value_;
};

class Pascal final : public Quantity {
 public:
  explicit Pascal(long long v) : value_(v) {}

 private:
  long long value() const override { return value_; }
  std::string unit() const override { return "Pa"; }
  long long value_;
};

int main() {
  [[maybe_unused]] const Celsius room{21};
  [[maybe_unused]] const Pascal air{101325};

  assert(room.describe() == "21 °C");  // 공통 동작은 얻었지만
  assert(room.less_than(air));         // 온도와 압력이 비교된다
  assert(Quantity::live == 2);         // 타입별로 세지 못한다
  static_assert(sizeof(Celsius) > sizeof(long long));  // 객체가 커졌다
}

문제의 뿌리는 하나입니다. Quantity는 자신을 상속한 타입이 무엇인지 모릅니다. 그래서 파생 타입의 함수를 부르려고 가상 함수 표 포인터를 객체마다 넣었고, 이 글의 검증 환경에서 객체는 16바이트가 됐습니다. 비교 함수의 매개변수에는 Celsius 대신 Quantity를 적을 수밖에 없습니다. 정적 변수도 Quantity에 하나뿐이라 두 타입이 함께 씁니다.

가상 함수는 실행 중에 타입이 정해질 때 쓰는 도구입니다. 여기서는 컴파일러가 이미 답을 알고 있습니다. 베이스에 그 답을 알려 주면 됩니다.

패턴 적용

파생 클래스가 자기 이름을 베이스 템플릿의 인자로 넘깁니다.

cpp일부 발췌 · 검증 제외
template <class Derived>
class Base { /* Derived라는 이름을 쓸 수 있다 */ };

class Widget : public Base<Widget> {};

이 구조를 이상하게 반복되는 템플릿 패턴(CRTP, Curiously Recurring Template Pattern)이라고 합니다. 1995년 James Coplien이 여러 코드에서 되풀이되는 모양을 보고 붙인 이름입니다. CRTP로 얻는 다형성은 어떤 함수를 부를지 컴파일할 때 정해지므로 정적 다형성(static polymorphism)이라고 부릅니다. 특정 기능 하나를 덧붙이려고 상속하는 작은 클래스는 믹스인(mixin)이라고 합니다.

믹스인 세 가지

요구 사항 세 개를 믹스인 세 개로 나눕니다. 베이스가 Derived를 쓰는 자리가 서로 다르다는 점을 눈여겨봐 주세요.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <string>
#include <type_traits>
#include <utility>

// 용도 1: 파생 타입의 함수를 부른다.
template <class Derived>
class Describable {
 public:
  std::string describe() const {
    const Derived& self = static_cast<const Derived&>(*this);
    return std::to_string(self.value()) + ' ' + self.unit();
  }

 private:
  Describable() = default;  // Derived만 만들 수 있다
  friend Derived;
};

// 용도 2: 함수 시그니처에 파생 타입의 이름을 적는다.
template <class Derived>
class Ordered {
  friend bool operator>(const Derived& a, const Derived& b) { return b < a; }
  friend bool operator<=(const Derived& a, const Derived& b) { return !(b < a); }
  friend bool operator>=(const Derived& a, const Derived& b) { return !(a < b); }

  Ordered() = default;
  friend Derived;
};

// 용도 3: 파생 타입마다 따로 있는 상태를 둔다.
template <class Derived>
class Counted {
 public:
  static int live() noexcept { return live_; }

 private:
  Counted() noexcept { ++live_; }
  Counted(const Counted&) noexcept { ++live_; }  // 복사도 이동도 새 객체를 만든다
  Counted& operator=(const Counted&) noexcept = default;
  ~Counted() { --live_; }
  friend Derived;

  static inline int live_ = 0;
};

용도 1의 static_cast<const Derived&>(*this)가 CRTP의 핵심입니다. *this가 실제로 Derived 객체의 일부일 때만 올바른 변환이며, 실행 중에 확인하지 않습니다. 이 전제는 뒤에서 private 생성자로 보호합니다.

용도 2에는 변환이 없습니다. Ordered<Celsius>가 인스턴스화될 때 Celsius 전용 비교 함수가 생깁니다. 클래스 안에서만 선언된 friend 함수는 그 클래스와 관련된 인자가 있을 때 인자 의존 탐색(ADL, argument-dependent lookup)으로만 찾을 수 있습니다. 이런 함수를 숨은 friend(hidden friend)라고 합니다.

용도 3은 템플릿의 성질을 이용합니다. Counted<Celsius>와 Counted<Pascal>은 서로 다른 클래스이므로 정적 변수도 따로 생깁니다. 복사 생성자를 직접 정의하면 이동 생성자는 자동으로 선언되지 않습니다. 그래서 파생 객체를 이동할 때도 이 복사 생성자가 불려 개수가 맞습니다. 개수를 세는 변수는 원자적(atomic)이지 않으므로 여러 스레드에서 쓰려면 std::atomic<int>로 바꿔야 합니다.

값 타입에 붙이기

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
class Celsius : public Describable<Celsius>, public Ordered<Celsius>, public Counted<Celsius> {
 public:
  explicit Celsius(long long v) : value_(v) {}
  long long value() const noexcept { return value_; }
  std::string unit() const { return "°C"; }
  friend bool operator<(const Celsius& a, const Celsius& b) { return a.value_ < b.value_; }

 private:
  long long value_;
};

class Pascal : public Describable<Pascal>, public Ordered<Pascal>, public Counted<Pascal> {
 public:
  explicit Pascal(long long v) : value_(v) {}
  long long value() const noexcept { return value_; }
  std::string unit() const { return "Pa"; }
  friend bool operator<(const Pascal& a, const Pascal& b) { return a.value_ < b.value_; }

 private:
  long long value_;
};

// 빈 베이스 셋을 붙여도 크기가 그대로다.
static_assert(sizeof(Celsius) == sizeof(long long));
static_assert(!std::is_polymorphic_v<Celsius>);
static_assert(!std::is_destructible_v<Counted<Celsius>>);  // 베이스 포인터로 delete할 수 없다

template <class A, class B>
concept Comparable = requires(const A& a, const B& b) { a > b; a <= b; a >= b; };
static_assert(Comparable<Celsius, Celsius>);
static_assert(!Comparable<Celsius, Pascal>);  // 온도와 압력은 비교되지 않는다

// 파생 타입의 공통 동작을 받는 함수. 가상 호출이 아니다.
template <class Derived>
std::string label(const Describable<Derived>& d) {
  return "[" + d.describe() + "]";
}

int main() {
  {
    [[maybe_unused]] const Celsius cold{-3};
    Celsius room{21};
    [[maybe_unused]] const Pascal air{101325};

    assert(room.describe() == "21 °C" && air.describe() == "101325 Pa");
    assert(label(room) == "[21 °C]");
    assert(room > cold && !(cold > room));
    assert(cold <= room && room <= room && !(room <= cold));
    assert(room >= cold && room >= room && !(cold >= room));

    assert(Celsius::live() == 2 && Pascal::live() == 1);
    room = Celsius{25};
    assert(Celsius::live() == 2);  // 대입은 객체를 늘리지 않고, 임시 객체는 사라졌다
    [[maybe_unused]] const Celsius moved = std::move(room);
    assert(Celsius::live() == 3);  // 이동된 원본도 아직 살아 있다
  }
  assert(Celsius::live() == 0 && Pascal::live() == 0);
}

네 요구 사항을 모두 만족합니다. describe에서 부르는 value와 unit은 보통의 멤버 함수 호출이라 인라인될 수 있습니다.

sizeof가 그대로인 것은 빈 베이스 최적화(EBO, empty base optimization) 덕분입니다. 빈 베이스는 다른 하위 객체와 주소를 겹쳐 쓸 수 있습니다. 실제 배치는 ABI가 정하며, 이 글의 두 컴파일러에서는 8바이트입니다. MSVC는 기본 설정에서 빈 베이스가 여럿이면 다 겹치지 않으므로, 파생 클래스에 __declspec(empty_bases)를 붙여야 합니다.

왜 컴파일되는가, 어디까지 되는가

Celsius를 정의하는 도중에 Describable<Celsius>가 필요합니다. 이때 Celsius는 아직 불완전 타입(incomplete type)입니다. 그런데도 self.unit()이 컴파일되는 이유는, 클래스 템플릿을 암묵적으로 인스턴스화할 때 멤버 함수의 선언만 만들고 정의는 쓰일 때 만들기 때문입니다. describe()를 부르는 시점에는 Celsius가 완성돼 있습니다.

반대로 클래스 본문에서 바로 Derived의 속을 들여다보면 오류가 납니다.

cpp컴파일 오류 예시
template <class Derived>
struct Measured {
  typename Derived::rep raw() const;  // 선언에 필요한 타입인데, Derived가 아직 불완전하다
};

struct Meter : Measured<Meter> {
  using rep = long long;
};

Derived가 개념(concept)을 만족하는지 확인하는 static_assert도 클래스 본문에는 둘 수 없습니다. 멤버 함수 본문이나 파생 클래스 정의 뒤에 둡니다. 반환 타입은 auto로 적으면 본문을 인스턴스화할 때까지 미룰 수 있습니다.

잘못된 상속 막기

CRTP에서 가장 위험한 실수는 복사해 붙인 뒤 인자를 고치지 않는 것입니다. class Pascal : public Describable<Celsius>라고 쓰면 static_cast는 문법상 문제가 없습니다. 실제로는 Celsius가 아닌 객체를 Celsius로 다루므로 미정의 동작(UB, undefined behavior)입니다. private 생성자와 friend Derived가 이 실수를 컴파일 오류로 바꿉니다.

cpp컴파일 오류 예시
template <class Derived>
class Describable {
  Describable() = default;
  friend Derived;
};

class Celsius : public Describable<Celsius> {};

class Pascal : public Describable<Celsius> {  // 실수: Pascal이어야 한다
 public:
  explicit Pascal(long long) {}
};

Describable<Celsius>의 생성자는 Celsius만 부를 수 있으므로 Pascal의 생성자가 거절됩니다. 이 장치에는 부작용이 하나 있습니다. 파생 클래스에 생성자가 없으면 C++17부터는 집합체(aggregate)가 될 수 있습니다. 그러면 Celsius{}가 호출한 쪽에서 베이스를 초기화하려다 실패합니다. 예제의 값 타입처럼 생성자를 직접 선언하면 됩니다.

Counted는 소멸자도 private입니다. 그래서 Counted<Celsius>*로 delete하는 코드도 막힙니다. 가상 소멸자가 없는 베이스로 지우면 UB이기 때문입니다. C++ Core Guidelines C.35도 베이스 소멸자를 "공개 가상" 아니면 "비가상 protected"로 두라고 권합니다.

트레이드오프

기준가상 함수CRTP
호출 대상이 정해지는 때실행 중컴파일할 때
객체 크기가상 함수 표 포인터가 붙는다빈 믹스인은 대개 0바이트
한 컨테이너에 섞어 담기베이스 포인터로 가능불가. Base<A>와 Base<B>는 다른 타입
구현을 빠뜨렸을 때객체를 만들 때 오류그 함수를 쓸 때 오류
파생의 파생다시 재정의 가능첫 단계에서 멈춘다
코드 위치와 크기구현을 .cpp에 둘 수 있다헤더에 두고, 타입마다 한 벌 생긴다
라이브러리 경계(ABI)넘길 수 있다양쪽이 같은 템플릿 정의를 봐야 한다

표에서 두 줄은 설명이 더 필요합니다.

  • 구현을 빠뜨렸을 때. 베이스의 공개 함수와 파생의 구현 함수에 같은 이름을 쓰지 마세요. 파생이 구현을 빠뜨리면 self.describe()가 베이스 자신을 다시 불러 무한 재귀가 됩니다. 이 글은 describe와 unit처럼 이름을 나눠, 빠뜨리면 컴파일 오류가 나게 했습니다.
  • 파생의 파생. Celsius를 다시 상속해 unit을 새로 정의해도 describe는 Celsius의 것을 부릅니다. 베이스가 아는 이름은 Celsius뿐이기 때문입니다.

쓰지 말아야 할 때도 분명합니다.

  • 타입을 실행 중에 고르거나 섞어 담아야 한다면 가상 함수, 6편의 std::variant, 7편의 타입 소거가 맞습니다.
  • "이 함수가 있어야 한다"는 요구 사항만 표현하려면 2편의 concept으로 충분합니다. 상속시키지 않아도 됩니다.
  • 파생 타입의 이름이 필요 없다면 일반 함수 템플릿이 더 단순합니다. describe(const T&)를 자유 함수로 두면 상속도 변환도 없습니다.
  • 호출 비용만 보고 바꾸지는 마세요. 이 글은 성능을 재지 않았습니다. 정확한 타입이 보이는 곳에서는 가상 호출도 직접 호출로 바뀔 수 있습니다.

현대 C++ 대안

용도 세 가지를 하나씩 다시 보겠습니다.

용도 2는 C++20 기본 비교가 대신한다

Ordered는 C++20에서 대부분 필요 없어졌습니다. operator<=>를 기본으로 만들면 네 개의 대소 비교가 모두 이 함수로 처리됩니다. operator==를 따로 선언하지 않았다면 그것도 함께 기본으로 선언됩니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <compare>

class Celsius {
 public:
  explicit Celsius(long long v) : value_(v) {}
  auto operator<=>(const Celsius&) const = default;

 private:
  long long value_;
};
static_assert(std::three_way_comparable<Celsius, std::strong_ordering>);

int main() {
  [[maybe_unused]] const Celsius cold{-3};
  [[maybe_unused]] const Celsius room{21};
  assert(cold < room && room > cold && cold <= room && room >= cold);
  assert(cold != room && room == room);
}

기본 비교는 멤버뿐 아니라 베이스도 차례로 비교합니다. 빈 믹스인이라도 비교 연산자가 없으면 기본 비교는 삭제됩니다.

cpp컴파일 오류 예시
#include <compare>

struct Tag {};  // 비교를 모르는 빈 믹스인
class Tagged : public Tag {
 public:
  explicit Tagged(long long v) : value_(v) {}
  auto operator<=>(const Tagged&) const = default;  // 삭제된 함수가 된다

 private:
  long long value_;
};

bool cooler(const Tagged& a, const Tagged& b) { return a < b; }

선언 자체는 오류가 아니라서, 비교를 실제로 쓰는 곳에서야 실패합니다. clang 18은 선언에 경고를 내지만 g++ 14는 -Wall -Wextra에서도 조용합니다.

본문의 Describable이나 Counted처럼 비교를 모르는 믹스인을 붙인 타입이라면 return value_ <=> other.value_;처럼 직접 적는 편이 간단합니다. 이때는 operator==가 자동으로 생기지 않으므로 함께 정의합니다.

용도 1은 deducing this가 대신한다

C++23의 명시적 객체 매개변수(explicit object parameter)는 this가 가리키던 객체를 첫 매개변수로 드러냅니다. 제안서의 별명인 deducing this로 더 널리 알려져 있습니다. 이 매개변수의 타입을 추론하게 하면 템플릿이 아닌 베이스도 호출한 객체의 타입을 알 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++23)
#include <cassert>
#include <string>
#include <type_traits>
#include <utility>

class Describable {  // 템플릿이 아니다
 public:
  std::string describe(this const auto& self) { return std::to_string(self.value()) + ' ' + self.unit(); }

  // 연쇄 호출: 호출한 객체의 타입과 값 범주를 그대로 돌려준다.
  template <class Self>
  Self&& offset(this Self&& self, long long by) {
    self.add(by);
    return std::forward<Self>(self);
  }
};

class Celsius : public Describable {
 public:
  explicit Celsius(long long v) : value_(v) {}
  long long value() const noexcept { return value_; }
  std::string unit() const { return "°C"; }
  void add(long long by) noexcept { value_ += by; }

 private:
  long long value_;
};

class Fahrenheit : public Celsius {  // 파생의 파생
 public:
  using Celsius::Celsius;
  std::string unit() const { return "°F"; }
};

static_assert(std::is_same_v<decltype(std::declval<Celsius&>().offset(1)), Celsius&>);
static_assert(std::is_same_v<decltype(std::declval<Celsius>().offset(1)), Celsius&&>);

int main() {
  Celsius room{21};
  assert(room.describe() == "21 °C");
  room.offset(1).offset(2);
  assert(room.value() == 24);
  [[maybe_unused]] const Celsius copy = Celsius{10}.offset(5);  // 임시 객체에서 이어 쓰기
  assert(copy.value() == 15);

  Fahrenheit f{70};
  assert(f.describe() == "70 °F");  // 정적 타입이 Fahrenheit다
  [[maybe_unused]] const Celsius& as_celsius = f;
  assert(as_celsius.describe() == "70 °C");  // 정적 타입이 Celsius다
}

static_cast, friend Derived, 잘못된 템플릿 인자가 모두 사라졌습니다. 연쇄 호출을 CRTP로 만들 때는 lvalue용과 rvalue용을 따로 써야 했지만, 여기서는 함수 하나입니다. 다만 rvalue에서 부르면 임시 객체를 가리키는 참조가 나옵니다. auto&& r = Celsius{10}.offset(5);처럼 이름을 붙이면 문장이 끝난 뒤 매달린 참조가 됩니다.

예제의 마지막 네 줄이 CRTP와 결정적으로 다른 점을 보여 줍니다. deducing this는 호출식의 정적 타입을 추론합니다. 실행 중의 타입을 찾는 것이 아니므로 가상 함수를 대신하지 않습니다. 그래서 파생의 파생은 잘 따라가지만, 베이스 참조로 부르면 파생 타입을 잃어버립니다.

cpp컴파일 오류 예시
struct Describable {
  int describe(this const auto& self) { return self.unit(); }
};
struct Celsius : Describable {
  int unit() const { return 1; }
};

int label(const Describable& d) { return d.describe(); }  // Self는 Describable이다

CRTP의 label(const Describable<Derived>&)은 베이스 참조로 받아도 Derived를 기억합니다. 타입 이름에 적혀 있기 때문입니다. deducing this로 옮긴다면 label도 const auto&를 받는 템플릿으로 바꿔야 합니다.

옮길 때 확인할 것이 세 가지 더 있습니다.

  • 명시적 객체 매개변수가 있는 함수 안에서는 this를 쓸 수 없고, 멤버 이름도 self.를 붙여야 합니다. 이런 함수는 virtual이나 static이 될 수 없습니다.
  • 베이스의 멤버를 self.x로 쓰면 파생 클래스의 같은 이름 멤버가 잡힐 수 있습니다.
  • 템플릿이 아닌 베이스를 여러 타입이 함께 쓰면 빈 베이스 최적화가 깨질 수 있습니다. 같은 타입의 하위 객체 둘은 크기가 0이어도 주소를 공유하지 못하기 때문입니다.

마지막 항목은 코드로 확인해 보겠습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <type_traits>

struct Plain {};  // 템플릿이 아닌 믹스인
struct PlainInner : Plain {
  long long v;
};
struct PlainOuter : Plain {  // 베이스 Plain과 첫 멤버 속의 Plain이 겹칠 수 없다
  PlainInner inner;
};
static_assert(std::is_empty_v<Plain>);
static_assert(sizeof(PlainOuter) > sizeof(PlainInner));

template <class Derived>
struct Mixin {};
struct Inner : Mixin<Inner> {
  long long v;
};
struct Outer : Mixin<Outer> {  // Mixin<Outer>와 Mixin<Inner>는 다른 타입이다
  Inner inner;
};
static_assert(sizeof(Outer) == sizeof(Inner));

int main() {}

표준 라이브러리도 이 문제를 겪었습니다. std::ranges::view_interface가 공통 베이스 view_base를 상속하도록 규정했다가, 어댑터를 겹칠 때 불필요한 패딩이 생겨 LWG 3549로 그 상속을 뺐습니다.

용도 3은 CRTP로 남는다

Counted는 deducing this로 바꿀 수 없습니다. 생성자와 소멸자에는 명시적 객체 매개변수를 쓸 수 없고, 템플릿이 아닌 베이스의 정적 변수는 하나뿐입니다. 파생 타입마다 다른 상태나 멤버 타입이 있으려면 베이스 자체가 달라야 합니다. 표준 라이브러리의 std::enable_shared_from_this<T>도 그래서 CRTP입니다. 이 베이스는 3편에서 본 weak_ptr를 weak_ptr<T> 멤버로 들고 있으므로, 멤버 함수를 부를 때가 아니라 클래스가 만들어질 때 T를 알아야 합니다.

베이스가 파생 타입을 쓰는 곳대안CRTP가 남는 경우
1. 파생의 함수를 부른다C++23 deducing thisC++20 이하, Base<D>&로 받아 D를 알아야 할 때, 빈 베이스가 겹칠 때
2. 시그니처에 파생 이름을 적는다비교는 C++20 <=>다른 연산자를 숨은 friend로 찍어 낼 때
3. 파생별 상태·멤버 타입을 둔다없음항상
요구 사항만 표현한다C++20 concept대개 없음

C++17이라면 <=>가 없으므로 Ordered가 여전히 쓸모 있습니다. 이때는 !=도 직접 추가해야 합니다. a != b를 !(a == b)로 바꿔 주는 규칙은 C++20에서 들어왔습니다.

정리

  • CRTP는 베이스에 파생 타입의 이름을 알려 줍니다. 타입이 컴파일할 때 모두 정해지고 한 목록에 섞을 필요가 없을 때 맞습니다.
  • 먼저 베이스가 그 이름을 어디에 쓰는지 봅니다. 함수 호출이면 deducing this, 비교 연산이면 <=>, 요구 사항 표현이면 concept이 더 단순합니다.
  • 파생별 상태와 멤버 타입, 베이스 참조로도 잃지 않아야 하는 타입 정보가 필요하면 CRTP를 남깁니다.
  • CRTP를 쓴다면 생성자를 private으로 두고 friend Derived를 적어 잘못된 상속을 막습니다. 공개 함수와 구현 함수의 이름은 나눕니다.
  • deducing this는 정적 타입을 추론할 뿐입니다. 실행 중의 다형성이 필요하면 가상 함수를 씁니다.

다음 편에서는 새 타입을 추가할 때 기존 생성 코드를 고치지 않는 등록 기반 팩토리와, 그때 만나는 정적 초기화 순서 문제를 다룹니다.
