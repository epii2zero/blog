RAII와 소유권 — 모든 패턴의 출발점

예외가 나거나 함수가 일찍 반환되어도 자원이 반드시 정리되게 하는 설계, RAII를 다룹니다. 직접 만든 핸들 래퍼에서 unique_ptr 사용자 삭제자, 스코프 가드, C++23 out_ptr까지, 소유권을 타입으로 표현하는 방법과 0/3/5의 규칙을 실행되는 예제로 정리합니다.

예외가 나거나 함수가 중간에 반환되어도 자원이 반드시 정리되게 하려면 무엇을 설계해야 할까요? 이 시리즈는 GoF 패턴을 현대 C++로 다시 읽습니다. 그 첫 편으로 패턴 목록에는 없지만 모든 패턴의 바탕이 되는 관용구, RAII를 다룹니다. 이 글을 읽고 나면 "이 자원은 누가 소유하나"를 타입으로 표현하고, 직접 만든 래퍼·std::unique_ptr·스코프 가드 가운데 무엇을 고를지 판단할 수 있습니다.

문제 상황

C 라이브러리를 감싸는 코드를 쓴다고 해 봅시다. 파일, 소켓, 데이터베이스 연결, 뮤텍스 잠금처럼 "열었으면 반드시 닫아야 하는" 자원이 나옵니다. 요구 사항은 단순합니다.

  • 연 자원은 함수가 어떤 경로로 끝나든 정확히 한 번 닫는다.
  • 정상 반환, return 조기 반환, 예외 전파가 모두 같은 규칙을 따른다.
  • 닫는 책임이 누구에게 있는지 코드를 읽고 알 수 있어야 한다.

세 번째 요구 사항이 중요합니다. 자원 정리 버그는 대부분 "닫는 코드를 깜빡했다"보다 "누가 닫아야 하는지 합의가 없었다"에서 나옵니다.

순진한 구현

예제가 실제 운영체제 자원에 기대지 않도록, 열린 핸들 수를 세는 가짜 C API를 먼저 만듭니다. open은 미리 잡아 둔 칸 하나를 내주고 카운터를 올립니다. close는 칸을 돌려받고 카운터를 내립니다. 힙 메모리를 쓰지 않으므로, 아래 예제의 "누수"는 카운터에만 남고 실제 메모리 누수는 생기지 않습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstdio>
#include <memory>
#include <stdexcept>
#include <string_view>
#include <type_traits>
#include <utility>

// C 스타일 가짜 API: 실제 파일 대신 "열린 핸들 수"만 센다.
namespace fake {
struct File {
  bool in_use = false;
};

inline File pool[4];
inline int open_count = 0;

inline File* open(const char* /*path*/) {
  for (File& f : pool) {
    if (!f.in_use) {
      f.in_use = true;
      ++open_count;
      return &f;
    }
  }
  return nullptr;  // 열 수 있는 칸이 없다
}

inline void close(File* f) {
  f->in_use = false;
  --open_count;
}

inline bool write(File*, std::string_view data) { return !data.empty(); }
}  // namespace fake

가장 먼저 떠오르는 코드는 이렇습니다. 열고, 쓰고, 닫습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
void save_naive(std::string_view text) {
  fake::File* f = fake::open("report.txt");
  if (f == nullptr) throw std::runtime_error("open 실패");
  if (!fake::write(f, text)) throw std::runtime_error("write 실패");  // 여기서 나가면
  fake::close(f);                                                     // 이 줄은 실행되지 않는다
}

void demo_naive() {
  save_naive("ok");
  assert(fake::open_count == 0);  // 정상 경로는 문제없다

  try {
    save_naive("");  // 빈 데이터 → write 실패 → 예외
  } catch (const std::runtime_error&) {
  }
  assert(fake::open_count == 1);  // 핸들 하나가 닫히지 않고 남았다

  fake::close(&fake::pool[0]);  // 다음 시연을 위해 직접 정리한다
  assert(fake::open_count == 0);
}

정상 경로는 잘 동작합니다. 그런데 write가 실패해 예외를 던지면 close를 건너뜁니다. assert(fake::open_count == 1)이 통과한다는 것이 곧 버그의 증거입니다. 실제 파일이었다면 파일 디스크립터 하나가 프로세스가 끝날 때까지 남습니다.

try/catch로 감싸 close를 두 군데 쓰면 이 함수 하나는 고칠 수 있습니다. 하지만 자원이 둘, 셋으로 늘면 정리 순서와 경로 조합이 빠르게 늘어납니다. 또 close를 부를 의무가 호출자에게 있는지, save_naive에 있는지가 여전히 코드에 드러나지 않습니다.

패턴 적용

RAII: 정리를 소멸자에 맡긴다

자원 획득은 초기화(RAII, Resource Acquisition Is Initialization)는 이름보다 반대쪽 절반이 더 중요한 관용구입니다. 자원을 객체의 생성자에서 얻고, 그 객체의 소멸자에서 돌려줍니다. C++은 스코프를 벗어나는 모든 자동 객체의 소멸자를 호출합니다. 예외로 스코프를 벗어날 때도 스택 되감기(stack unwinding) 과정에서 소멸자가 불립니다. 그래서 정리 코드를 "모든 경로에 하나씩" 쓰는 대신 소멸자 한 곳에 씁니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
class File {
 public:
  explicit File(const char* path) : f_(fake::open(path)) {
    if (f_ == nullptr) throw std::runtime_error("open 실패");
  }
  ~File() { reset(); }

  // 복사하면 같은 핸들을 두 번 닫게 되므로 금지한다.
  File(const File&) = delete;
  File& operator=(const File&) = delete;

  // 이동은 소유권을 넘긴다. 원본은 빈 상태가 된다.
  File(File&& other) noexcept : f_(std::exchange(other.f_, nullptr)) {}
  File& operator=(File&& other) noexcept {
    if (this != &other) {
      reset();
      f_ = std::exchange(other.f_, nullptr);
    }
    return *this;
  }

  fake::File* get() const noexcept { return f_; }

 private:
  void reset() noexcept {
    if (f_ != nullptr) fake::close(std::exchange(f_, nullptr));
  }

  fake::File* f_;
};

void save_raii(std::string_view text) {
  File f("report.txt");
  if (!fake::write(f.get(), text)) throw std::runtime_error("write 실패");
}  // 어떤 경로로 나가든 여기서 ~File()이 close를 부른다

void demo_raii() {
  try {
    save_raii("");
  } catch (const std::runtime_error&) {
  }
  assert(fake::open_count == 0);  // 예외 경로에서도 닫혔다

  File a("a.txt");
  File b = std::move(a);  // 소유권 이동: a는 비고 b가 닫을 책임을 진다
  assert(a.get() == nullptr && b.get() != nullptr);
  assert(fake::open_count == 1);
}  // b만 close를 부른다. a는 빈 상태라 아무것도 하지 않는다

save_raii에는 정리 코드가 한 줄도 없습니다. 그런데도 예외 경로에서 카운터가 0으로 돌아옵니다. 이 클래스에는 세 가지 설계 결정이 들어 있습니다.

  1. 생성자가 실패하면 예외를 던집니다. 객체가 존재한다는 것 자체가 "자원을 쥐고 있다"는 보장이 됩니다. 생성자가 끝나지 않은 객체의 소멸자는 불리지 않으므로, 이 보장이 깨지지 않습니다.
  2. 복사를 금지합니다. 핸들을 그대로 복사하면 두 객체가 같은 핸들을 닫으려 합니다.
  3. 이동을 허용하고 원본을 비웁니다. 그래서 File을 함수에서 반환하거나 컨테이너에 넣을 수 있습니다. 이동 연산은 noexcept로 둡니다. std::vector 같은 표준 컨테이너는 재할당 중 예외가 나도 원래 상태를 지키려고 std::move_if_noexcept를 씁니다. 이동이 noexcept가 아니면, 복사할 수 있는 타입은 이동 대신 복사됩니다.

소유와 대여를 타입으로 구분한다

RAII 객체가 생기면 함수 시그니처가 소유권을 말해 줍니다. 원칙은 간단합니다.

시그니처뜻
void f(File&), void f(fake::File*)대여(borrow). 잠깐 쓰기만 하고 닫지 않는다
void f(File) (값으로 받기)소유권을 넘겨받는다. 함수가 끝나면 닫힌다
File f() (값으로 반환)소유권을 호출자에게 넘긴다

원시 포인터(raw pointer)나 참조는 "소유하지 않는다"는 뜻으로만 씁니다. C++ 핵심 가이드라인(C++ Core Guidelines)의 R.3·R.4와 F.7이 이 규칙을 권합니다. 표의 "값으로 받기" 행은 R.32가 권하는 소유권 이전 방식입니다. 이 규칙을 지키면 "이 포인터를 내가 지워야 하나?"를 시그니처만 보고 답할 수 있습니다.

std::unique_ptr와 사용자 삭제자

File 클래스의 이동·복사 규칙은 사실 std::unique_ptr가 이미 구현해 둔 것과 같습니다. C API가 포인터 모양의 핸들을 준다면, 삭제자(deleter)만 바꿔 끼워 같은 효과를 얻을 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
struct FileCloser {
  void operator()(fake::File* f) const noexcept { fake::close(f); }
};
using UniqueFile = std::unique_ptr<fake::File, FileCloser>;

UniqueFile open_unique(const char* path) {
  UniqueFile f{fake::open(path)};
  if (!f) throw std::runtime_error("open 실패");
  return f;
}

// 대여: 닫을 책임이 없다는 것을 원시 포인터로 표현한다.
bool append(fake::File* f, std::string_view line) { return fake::write(f, line); }

// 소유권 이전: 값으로 받았으므로 이 함수가 끝나면 닫힌다.
void archive(UniqueFile f) {
  if (f) append(f.get(), "archived");
}  // f의 소멸자가 여기서 close를 부른다

// 빈 삭제자는 공간을 차지하지 않는다(g++ 14·clang 18 + libstdc++에서 확인).
static_assert(sizeof(UniqueFile) == sizeof(fake::File*));

void demo_unique_ptr() {
  UniqueFile f = open_unique("log.txt");
  [[maybe_unused]] const bool written = append(f.get(), "first line");
  assert(written);  // 상태를 바꾸는 호출은 assert 밖에 둔다(NDEBUG에서도 실행되도록)
  assert(fake::open_count == 2);  // main에서 연 g와 여기서 연 f

  archive(std::move(f));  // 소유권을 넘기는 지점이 std::move로 눈에 보인다
  assert(f == nullptr);
  assert(fake::open_count == 1);
}

demo_unique_ptr를 부르기 전에 main에서 핸들 하나를 더 열어 두었습니다(아래 g). 그래서 카운터가 2에서 1로 줄어드는 것으로 archive가 닫았다는 것을 확인합니다.

사용자 삭제자를 쓸 때 기억할 점이 두 가지 있습니다.

  • unique_ptr는 널 포인터에는 삭제자를 부르지 않습니다. 그래서 close(nullptr)를 걱정하지 않아도 됩니다.
  • 삭제자는 타입의 일부입니다. 삭제자가 다르면 unique_ptr<T, D1>과 unique_ptr<T, D2>는 다른 타입입니다. 상태 없는 함수 객체를 쓰면 주요 구현(libstdc++, libc++, MSVC STL)에서는 크기 비용도 없습니다. 표준이 보장하는 성질은 아닙니다. 반면 함수 포인터를 삭제자로 쓰면 포인터 하나만큼 커집니다.

unique_ptr가 맞지 않는 경우도 있습니다. 핸들이 int 파일 디스크립터처럼 포인터가 아닌 경우입니다. 이때 unique_ptr를 억지로 쓰려면 삭제자에 별도의 pointer 타입을 정의해야 해서 코드가 오히려 복잡해집니다. 위의 File 같은 작은 래퍼를 직접 쓰는 편이 낫습니다.

0/3/5의 규칙

File에는 특수 멤버 함수 다섯 개(소멸자, 복사 생성자, 복사 대입, 이동 생성자, 이동 대입)를 모두 직접 적었습니다. 이것이 5의 규칙(rule of five)입니다. 다섯 가운데 하나라도 직접 정의하거나 삭제한다면, 나머지도 모두 의도를 밝혀 적으라는 규칙입니다(Core Guidelines C.21). 이동이 없던 C++03 시절에는 앞의 셋만 있었으므로 3의 규칙이라고 불렀습니다.

더 중요한 것은 0의 규칙(rule of zero)입니다. 자원을 직접 다루는 클래스는 File처럼 자원 하나만 맡게 합니다. 나머지 클래스는 그런 RAII 멤버를 조합하기만 하고 특수 멤버 함수를 하나도 쓰지 않습니다(C.20). 컴파일러가 멤버별로 알맞은 연산을 만들어 줍니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
class Report {
 public:
  explicit Report(const char* path) : out_(open_unique(path)) {}
  bool add(std::string_view line) {
    if (!append(out_.get(), line)) return false;
    ++lines_;
    return true;
  }
  int lines() const noexcept { return lines_; }

 private:
  UniqueFile out_;   // 이동만 가능
  int lines_ = 0;    // 복사·이동 모두 가능
};

// 특수 멤버 함수를 하나도 쓰지 않았지만, 멤버를 따라 "이동만 가능"한 타입이 된다.
static_assert(!std::is_copy_constructible_v<Report>);
static_assert(std::is_nothrow_move_constructible_v<Report>);
// 소멸자는 따로 적지 않아도 noexcept다.
static_assert(std::is_nothrow_destructible_v<Report>);

int main() {
  demo_naive();
  demo_raii();
  assert(fake::open_count == 0);

  UniqueFile g = open_unique("keep.txt");
  demo_unique_ptr();
  assert(fake::open_count == 1);  // g만 남았다

  {
    Report r("report.txt");
    [[maybe_unused]] const bool added = r.add("hello");
    assert(added);
    Report moved = std::move(r);
    assert(moved.lines() == 1);
    assert(fake::open_count == 2);
  }
  assert(fake::open_count == 1);

  g.reset();
  assert(fake::open_count == 0);
  std::puts("모든 핸들이 정확히 한 번씩 닫혔습니다");
}

Report는 소멸자도, 이동 생성자도 직접 쓰지 않았습니다. 그래도 복사는 막히고 이동은 noexcept로 됩니다. 멤버 UniqueFile이 그렇게 생겼기 때문입니다. static_assert로 확인했듯이 이 성질은 컴파일 시점에 정해집니다. 클래스에 소멸자를 직접 쓰고 싶어진다면, 그 자원을 맡을 작은 RAII 타입을 먼저 만들 수 있는지 살펴보세요.

스코프 가드: 이름 없는 정리 작업

모든 정리 작업이 "자원 하나"의 모양을 하고 있지는 않습니다. 예를 들어 여러 단계를 거치는 작업 도중 실패하면 앞 단계를 되돌려야 하는 트랜잭션(transaction)이 있습니다. 매번 클래스를 만들기에는 일이 작습니다. 이럴 때 스코프 가드(scope guard)를 씁니다. 스코프를 벗어날 때 실행할 함수를 들고 있다가, 성공하면 dismiss()로 해제하는 작은 RAII 객체입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <concepts>
#include <stdexcept>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

template <std::invocable F>
class [[nodiscard]] ScopeGuard {
 public:
  [[nodiscard]] explicit ScopeGuard(F f) noexcept(std::is_nothrow_move_constructible_v<F>)
      : f_(std::move(f)) {}

  // 이동하면 원본은 해제되어, 정리 작업이 두 번 실행되지 않는다.
  ScopeGuard(ScopeGuard&& other) noexcept(std::is_nothrow_move_constructible_v<F>)
      : f_(std::move(other.f_)), active_(std::exchange(other.active_, false)) {}

  ScopeGuard(const ScopeGuard&) = delete;
  ScopeGuard& operator=(const ScopeGuard&) = delete;
  ScopeGuard& operator=(ScopeGuard&&) = delete;

  ~ScopeGuard() {
    if (active_) f_();  // 소멸자는 암묵적으로 noexcept: f_가 던지면 std::terminate
  }

  void dismiss() noexcept { active_ = false; }

 private:
  F f_;
  bool active_ = true;
};

struct Inventory {
  std::vector<std::string> items;
  std::vector<std::string> audit_log;
};

// 두 단계 갱신: 두 번째 단계가 실패하면 첫 단계를 되돌린다.
void add_item(Inventory& inv, const std::string& name, bool audit_ok) {
  inv.items.push_back(name);
  ScopeGuard rollback{[&inv]() noexcept { inv.items.pop_back(); }};

  if (!audit_ok) throw std::runtime_error("감사 로그 기록 실패");
  inv.audit_log.push_back("added " + name);

  rollback.dismiss();  // 모든 단계가 성공했으니 되돌리지 않는다
}

int main() {
  Inventory inv;
  add_item(inv, "apple", true);
  assert(inv.items.size() == 1 && inv.audit_log.size() == 1);

  try {
    add_item(inv, "banana", false);
  } catch (const std::runtime_error&) {
  }
  // 실패한 갱신은 흔적을 남기지 않았다.
  assert(inv.items.size() == 1 && inv.items.back() == "apple");
  assert(inv.audit_log.size() == 1);

  // 이동한 가드는 정리 작업을 한 번만 실행한다.
  int runs = 0;
  {
    ScopeGuard a{[&runs]() noexcept { ++runs; }};
    ScopeGuard b = std::move(a);
  }
  assert(runs == 1);
}

이 작은 클래스에도 RAII의 규칙이 그대로 적용됩니다.

  • 이동 전용 타입입니다. 이동 생성자는 원본의 active_를 끕니다. 이동 대입은 막았습니다. 대입받는 쪽에 이미 걸린 정리 작업을 언제 실행할지 정하기 애매하기 때문입니다.
  • 클래스와 생성자 양쪽에 [[nodiscard]]를 붙였습니다. ScopeGuard{...};처럼 변수 이름을 빠뜨리면 가드가 그 줄에서 바로 사라집니다. C++20은 이렇게 임시 객체를 만들고 버리는 식에도 경고를 권합니다(P1771R1). 다만 경고는 권고 사항이라 컴파일러마다 다릅니다. clang 18은 클래스에만 붙여도 경고하지만, g++ 14는 생성자에 붙였을 때만 경고했습니다. 그래서 둘 다 붙였습니다.
  • 템플릿 인자를 std::invocable 개념(concept)으로 제약했습니다. 인자 없이 호출할 수 없는 것을 넘기면 가드 안쪽 깊은 곳이 아니라 선언 지점에서 오류가 납니다.

소멸자에서 예외를 던지면 안 되는 이유

RAII는 "소멸자는 실패하지 않는다"는 전제 위에 서 있습니다. C++11부터 소멸자는 따로 적지 않아도 noexcept입니다. 멤버나 기반 클래스의 소멸자가 예외를 허용하지 않는 한 그렇습니다. 그래서 다음 코드는 예외를 던지는 순간 std::terminate로 프로그램을 끝냅니다.

cpp일부 발췌 · 검증 제외
struct Bad {
  ~Bad() { throw std::runtime_error("닫기 실패"); }  // 암묵적 noexcept → std::terminate
};

~Bad() noexcept(false)로 바꿔도 문제는 남습니다. 다른 예외로 스택을 되감는 도중에 소멸자가 또 예외를 던지면, 표준은 무조건 std::terminate를 부릅니다. 되감기 중인 예외와 새 예외 가운데 무엇을 전파할지 정할 방법이 없기 때문입니다.

그렇다면 fclose처럼 정리 자체가 실패할 수 있는 경우는 어떻게 할까요? 실패를 알아야 하는 호출자를 위해 명시적인 close() 멤버를 따로 둡니다. 이 함수는 오류를 반환하거나 예외를 던질 수 있습니다. 소멸자는 아직 닫히지 않았을 때만 닫고, 오류는 기록만 하고 삼킵니다(Core Guidelines C.36, C.37).

트레이드오프

RAII는 비용이 거의 없는 관용구지만, 도구마다 맞는 자리가 다릅니다.

도구맞는 경우비용·제약쓰지 말아야 할 때
직접 만든 RAII 클래스포인터가 아닌 핸들(int fd 등), 자원별 추가 연산이 필요할 때5개 특수 멤버를 정확히 써야 한다. 실수할 여지가 있다unique_ptr + 삭제자로 충분할 때
unique_ptr<T, D>포인터 모양 핸들, 단독 소유상태 없는 삭제자면 주요 구현에서 원시 포인터와 크기가 같다(표준 보장은 아님). 삭제자가 타입의 일부다소유권을 여러 곳이 나눠 가져야 할 때
shared_ptr<T>소유자가 여럿이고 마지막 소유자를 미리 알 수 없을 때제어 블록 할당과 원자적 참조 계수 비용. 순환 참조는 풀리지 않는다"편해서" 쓰는 경우. 소유 관계가 흐려진다
스코프 가드한 함수 안의 되돌리기·후처리람다 캡처가 가리키는 대상의 수명을 직접 챙겨야 한다같은 정리가 여러 곳에서 반복될 때(이름 있는 RAII 타입으로 승격)

공유 소유권과 순환 참조, 그리고 이를 끊는 weak_ptr는 3편 Observer에서 수명 문제와 함께 다룹니다.

RAII가 도움이 안 되는 경우도 알아 둘 만합니다.

  • 소멸 순서를 정밀하게 조절해야 할 때: 같은 스코프의 자동 객체는 선언의 역순으로 소멸합니다. 이 순서가 맞지 않으면 선언 순서를 바꾸거나 스코프를 나눠야 합니다.
  • 정리에 시간이 오래 걸리거나 실패를 처리해야 할 때: 앞에서 본 대로 소멸자는 실패를 보고할 수 없습니다. 이런 정리는 명시적인 함수 호출로 드러내고, 소멸자는 안전망으로만 씁니다.
  • 프로세스 경계를 넘는 자원: 다른 프로세스가 잡은 파일 잠금처럼 이 프로세스의 스코프와 무관한 자원은 RAII만으로 정리를 보장할 수 없습니다. 프로세스가 강제 종료되면 소멸자도 불리지 않습니다.

현대 C++ 대안

RAII는 C++98부터 있던 관용구입니다. 그 뒤 표준이 바뀌면서 RAII 타입을 쓰기가 점점 쉬워졌습니다.

C++17: 보장된 복사 생략

C++17부터는 함수가 같은 타입의 prvalue(이름 없는 임시 값)를 반환하면 복사·이동 없이 호출자의 객체를 바로 초기화합니다(P0135R1). 그래서 이동조차 불가능한 RAII 타입도 팩토리 함수로 만들 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <mutex>

// 잠금 상태를 밖에서 볼 수 있는 가짜 뮤텍스(BasicLockable: lock/unlock만 있으면 된다)
struct FakeMutex {
  bool locked = false;
  void lock() { locked = true; }
  void unlock() { locked = false; }
};

// 복사도 이동도 안 되는 잠금 객체
class [[nodiscard]] Locked {
 public:
  explicit Locked(FakeMutex& m) : lock_(m) {}
  Locked(const Locked&) = delete;
  Locked(Locked&&) = delete;

 private:
  std::lock_guard<FakeMutex> lock_;
};

Locked lock(FakeMutex& m) { return Locked{m}; }  // C++17: 이동 생성자 없이도 컴파일된다

int main() {
  FakeMutex m;
  {
    Locked held = lock(m);
    assert(m.locked);  // 잠겨 있다
  }
  assert(!m.locked);  // 스코프를 벗어나 풀렸다
}

C++14까지는 이 코드가 컴파일되지 않았습니다. 실제로 이동이 생략되더라도 이동 생성자가 접근 가능해야 했기 때문입니다. 예제에서 std::mutex 대신 가짜 뮤텍스를 쓴 이유도 있습니다. 이미 잠근 스레드가 같은 std::mutex에 try_lock()을 부르면 표준상 정의되지 않은 동작이라, 잠금 상태를 확인하는 데 쓸 수 없습니다. std::lock_guard는 lock()과 unlock()만 있으면 어떤 타입이든 감쌀 수 있습니다.

C++20: 개념과 [[nodiscard]] 확장

앞의 ScopeGuard에 쓴 두 기능입니다. std::invocable로 템플릿 인자를 제약하면 잘못된 사용을 선언 지점에서 잡습니다. 생성자에 붙이는 [[nodiscard]]는 이름 없는 가드 실수를 잡습니다. [[nodiscard("이유")]]처럼 경고에 이유 문장을 붙일 수도 있습니다(P1301R4).

C++20에서는 평가되지 않는 문맥에도 람다를 쓸 수 있고(P0315R4), 캡처 없는 람다를 기본 생성할 수 있습니다(P0624R2). unique_ptr는 삭제자를 기본 생성하므로 두 기능이 모두 필요합니다. 그래서 삭제자를 std::unique_ptr<fake::File, decltype([](fake::File* f) { fake::close(f); })>처럼 한 줄로 쓸 수도 있습니다. 다만 이 타입은 오류 메시지에서 읽기 어렵습니다. 여러 곳에서 같은 타입을 써야 한다면 FileCloser처럼 이름 있는 함수 객체가 의도를 더 잘 드러냅니다.

C++23: std::out_ptr

C API는 자원을 반환값이 아니라 출력 매개변수(T**)로 돌려주는 경우가 많습니다. 이때 unique_ptr에 바로 넣을 방법이 없어서, 원시 포인터 변수를 거쳐 reset하는 코드를 반복해 써 왔습니다. C++23의 std::out_ptr(P1132R8)는 이 중간 단계를 없앱니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++23)
#include <cassert>
#include <memory>

namespace fake {
struct Conn {
  bool in_use = false;
};
inline Conn slot;
inline int open_count = 0;

// 성공하면 0을 반환하고 *out에 핸들을 쓴다 (C 라이브러리에 흔한 모양).
inline int connect(Conn** out) {
  slot.in_use = true;
  ++open_count;
  *out = &slot;
  return 0;
}
inline void disconnect(Conn* c) {
  c->in_use = false;
  --open_count;
}
}  // namespace fake

struct Disconnect {
  void operator()(fake::Conn* c) const noexcept { fake::disconnect(c); }
};
using UniqueConn = std::unique_ptr<fake::Conn, Disconnect>;

int main() {
  {
    // C++17/20: 원시 포인터를 거쳐 소유권을 넘긴다.
    UniqueConn conn;
    fake::Conn* raw = nullptr;
    if (fake::connect(&raw) == 0) conn.reset(raw);
    assert(conn && fake::open_count == 1);
  }
  assert(fake::open_count == 0);

  {
    // C++23: out_ptr가 임시 T**를 만들어 주고, 식이 끝날 때 conn.reset()을 부른다.
    UniqueConn conn;
    [[maybe_unused]] int rc = fake::connect(std::out_ptr(conn));
    assert(rc == 0 && conn && fake::open_count == 1);
  }
  assert(fake::open_count == 0);
}

이 예제는 g++ 14와 clang 18(libstdc++ 14) 모두 -std=c++23에서 통과했습니다. 기존 핸들을 넘기고 새 핸들을 받는 realloc 모양의 API에는 std::inout_ptr를 씁니다.

아직 표준이 아닌 것: scope_exit와 unique_resource

이 글의 ScopeGuard와 File을 일반화한 std::experimental::scope_exit·scope_fail·scope_success와 unique_resource가 제안되어 있습니다(P0052R10). 지금은 Library Fundamentals TS v3에 들어 있고, C++ 표준 본문에는 들어오지 않았습니다. 표준 라이브러리 구현마다 제공 여부가 달라서, 이 글은 직접 구현한 버전을 썼습니다.

정리

  • 정리해야 하는 자원이 있으면, 정리 코드를 경로마다 쓰지 말고 소멸자 한 곳에 둡니다.
  • 소유는 값(File, unique_ptr)으로, 대여는 참조나 원시 포인터로 표현합니다. 시그니처만 보고 닫을 책임을 알 수 있어야 합니다.
  • 포인터 모양 핸들은 unique_ptr와 상태 없는 삭제자로 충분합니다. 포인터가 아닌 핸들은 작은 RAII 클래스를 직접 씁니다.
  • 자원을 직접 다루는 클래스만 5의 규칙을 따르고, 나머지 클래스는 0의 규칙으로 조합합니다.
  • 소멸자는 실패하지 않게 씁니다. 실패를 알려야 하는 정리는 명시적인 close()로 드러냅니다.
