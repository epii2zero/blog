Strategy와 Policy 기반 설계 — 런타임 vs 컴파일타임

바뀌는 알고리즘을 갈아 끼우는 Strategy 패턴을 가상 함수, std::function, 템플릿 정책 세 방식으로 구현하고 같은 테스트로 검증합니다. 바인딩 시점·호출 비용·ABI 경계로 고르는 법과 C++20 concept, C++23 move_only_function을 다룹니다.

바뀌는 알고리즘을 갈아 끼워야 할 때, 가상 함수·std::function·템플릿 정책 가운데 무엇을 언제 고를까요? 이 글은 GoF의 Strategy 패턴을 세 방식으로 구현하고, 세 구현을 같은 테스트로 검증합니다. 다 읽고 나면 "정책을 언제 정하는가(바인딩 시점)"를 기준으로 방식을 고르고, 템플릿 정책의 요구 사항을 C++20 concept으로 적을 수 있습니다. 1편에서 다룬 소유권 표현(std::unique_ptr, 값, 참조)을 그대로 씁니다.

문제 상황

원격 서비스를 부르는 클라이언트를 만든다고 해 봅시다. 네트워크 호출은 가끔 실패하므로 다시 시도(retry)해야 합니다. 그런데 "얼마나 기다렸다가, 몇 번까지 다시 할지"는 호출 대상마다 다릅니다.

  • 내부 캐시 서버: 100ms 간격으로 최대 4번 시도한다(고정 간격).
  • 외부 결제 API: 100ms에서 시작해 실패할 때마다 대기를 두 배로 늘리되, 400ms를 넘기지 않고 최대 5번 시도한다(지수 백오프, exponential backoff).
  • 앞으로 다른 규칙(전체 대기 예산, 무작위 지연 등)이 더 생길 수 있다.
  • 재시도 규칙은 테스트에서 실제로 기다리지 않고 검증할 수 있어야 한다.

마지막 요구 사항부터 해결해 두겠습니다. 재시도 코드가 std::this_thread::sleep_for를 직접 부르면 테스트가 실제 시간만큼 느려집니다. 그래서 "기다리기"를 시계 객체에 맡기고, 테스트에서는 기다리지 않고 시각만 앞으로 옮기는 가짜 시계(fake clock)를 넣습니다. 원격 서비스도 "처음 N번 실패하고 그다음부터 성공하는" 가짜로 바꿉니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <algorithm>
#include <cassert>
#include <chrono>
#include <cstdio>
#include <functional>
#include <memory>
#include <optional>
#include <utility>
#include <vector>

using Millis = std::chrono::milliseconds;
using namespace std::chrono_literals;

// 가짜 시계: sleep_for는 기다리지 않고 "지금"만 앞으로 옮긴다.
class FakeClock {
 public:
  Millis now() const noexcept { return now_; }
  void sleep_for(Millis d) noexcept { now_ += d; }

 private:
  Millis now_{0};
};

// 처음 failures번은 실패하고, 그다음부터 성공하는 가짜 원격 호출
class FlakyService {
 public:
  explicit FlakyService(int failures) : failures_left_(failures) {}
  bool call() {
    ++calls_;
    if (failures_left_ == 0) return true;
    --failures_left_;
    return false;
  }
  int calls() const noexcept { return calls_; }

 private:
  int failures_left_;
  int calls_ = 0;
};

// n번째 실패 뒤의 대기 시간: initial, 2×initial, 4×initial, … 단 cap을 넘지 않는다.
// 1 << n처럼 바로 계산하면 n이 커질 때 오버플로(미정의 동작)가 나므로, cap에 닿을 때까지만 두 배로 늘린다.
Millis capped_backoff(Millis initial, Millis cap, int n) {
  Millis d = initial;
  for (int i = 1; i < n && d < cap; ++i) d *= 2;
  return std::min(d, cap);
}

// 테스트 도우미: 서비스와 시계를 새로 만들어 run을 한 번 돌리고 결과를 모은다.
struct Outcome {
  bool ok;
  int calls;
  Millis waited;
  bool operator==(const Outcome&) const = default;
};

template <class Run>
Outcome simulate(int failures, Run run) {
  FlakyService svc(failures);
  FakeClock clock;
  const bool ok = run(svc, clock);
  return {ok, svc.calls(), clock.now()};
}

Outcome의 operator==는 C++20의 기본 비교(defaulted comparison)로 만들었습니다. 결과를 assert(a == Outcome{…}) 한 줄로 확인하기 위해서입니다.

순진한 구현

가장 먼저 떠오르는 코드는 규칙의 종류를 열거형으로 받고 switch로 나누는 것입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
enum class RetryKind { fixed, exponential };

// 재시도 규칙이 호출 코드 안에 박혀 있다.
bool fetch_naive(FlakyService& svc, FakeClock& clock, RetryKind kind) {
  constexpr int max_attempts = 4;
  for (int failures = 0;;) {
    if (svc.call()) return true;
    if (++failures == max_attempts) return false;
    switch (kind) {
      case RetryKind::fixed:
        clock.sleep_for(100ms);
        break;
      case RetryKind::exponential:
        clock.sleep_for(capped_backoff(100ms, 400ms, failures));
        break;
    }
  }
}

void demo_naive() {
  [[maybe_unused]] const Outcome r = simulate(2, [](FlakyService& s, FakeClock& c) {
    return fetch_naive(s, c, RetryKind::exponential);
  });
  assert((r == Outcome{true, 3, 300ms}));  // 두 번 실패, 100ms + 200ms 기다린 뒤 성공
}

이 코드는 지금 요구 사항 두 개를 만족하고 테스트도 통과합니다. 문제는 요구 사항이 바뀔 때 드러납니다.

  • 결제 API는 최대 5번이어야 하는데, max_attempts가 함수 안의 상수입니다. 대상마다 다른 값을 쓰려면 매개변수가 계속 늘어납니다.
  • 새 규칙("전체 대기 500ms까지")을 넣으려면 RetryKind와 fetch_naive를 함께 고쳐야 합니다. 이 열거형으로 분기하는 곳이 여러 군데라면 그곳을 모두 찾아 고쳐야 합니다.
  • 재시도 규칙만 따로 테스트할 수 없습니다. 규칙을 확인하려면 항상 서비스 호출 루프를 함께 돌려야 합니다.

세 문제의 원인은 같습니다. "언제, 얼마나 다시 할지"라는 바뀌는 부분과 "호출하고, 실패하면 기다린다"라는 바뀌지 않는 부분이 한 함수에 섞여 있습니다.

패턴 적용

Strategy 패턴은 바뀌는 알고리즘을 별도 객체로 떼어 내고, 쓰는 쪽(문맥, context)은 그 객체에 일을 맡기기만 하는 구조입니다. GoF 책은 이를 "알고리즘군을 정의하고 각각을 캡슐화해 서로 바꿔 쓸 수 있게 한다"고 설명합니다.

먼저 전략이 답할 질문을 하나로 정합니다. "지금까지 failures번 실패했다. 얼마나 기다렸다가 다시 할까, 아니면 그만둘까?" C++로는 std::optional<Millis> next_delay(int failures)입니다. 값이 없으면(std::nullopt) 그만둔다는 뜻입니다. 최대 시도 횟수도 이렇게 전략 안으로 들어갑니다.

이 질문 하나를 C++에서 표현하는 방법은 세 가지입니다.

방법 1: 인터페이스 상속

GoF 책의 구조를 그대로 옮긴 방식입니다. 추상 클래스가 인터페이스를 정하고, 구체 전략이 상속해 구현합니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
namespace virt {

class RetryStrategy {
 public:
  virtual ~RetryStrategy() = default;
  virtual std::optional<Millis> next_delay(int failures) const = 0;

 protected:
  // 파생 객체를 기반 클래스 값으로 복사하면 파생 부분이 잘려 나가므로(슬라이싱) 공개하지 않는다(Core Guidelines C.67).
  RetryStrategy() = default;
  RetryStrategy(const RetryStrategy&) = default;
  RetryStrategy& operator=(const RetryStrategy&) = default;
};

class FixedDelay final : public RetryStrategy {
 public:
  FixedDelay(Millis delay, int max_attempts) : delay_(delay), max_attempts_(max_attempts) {}
  std::optional<Millis> next_delay(int failures) const override {
    if (failures >= max_attempts_) return std::nullopt;
    return delay_;
  }

 private:
  Millis delay_;
  int max_attempts_;
};

class ExponentialBackoff final : public RetryStrategy {
 public:
  ExponentialBackoff(Millis initial, Millis cap, int max_attempts)
      : initial_(initial), cap_(cap), max_attempts_(max_attempts) {}
  std::optional<Millis> next_delay(int failures) const override {
    if (failures >= max_attempts_) return std::nullopt;
    return capped_backoff(initial_, cap_, failures);
  }

 private:
  Millis initial_;
  Millis cap_;
  int max_attempts_;
};

// 문맥: 전략을 소유하고 일을 맡긴다. 실행 중에 전략을 바꿀 수도 있다.
class Client {
 public:
  explicit Client(std::unique_ptr<RetryStrategy> retry) : retry_(std::move(retry)) { assert(retry_); }
  void set_retry(std::unique_ptr<RetryStrategy> retry) {
    assert(retry);
    retry_ = std::move(retry);
  }

  bool fetch(FlakyService& svc, FakeClock& clock) const {
    for (int failures = 0;;) {
      if (svc.call()) return true;
      const std::optional<Millis> delay = retry_->next_delay(++failures);
      if (!delay) return false;
      clock.sleep_for(*delay);
    }
  }

 private:
  std::unique_ptr<RetryStrategy> retry_;  // 널이 아님
};

void demo_swap() {
  Client client{std::make_unique<FixedDelay>(100ms, 4)};
  auto run = [&client](FlakyService& s, FakeClock& c) { return client.fetch(s, c); };

  [[maybe_unused]] const Outcome before = simulate(1, run);
  assert((before == Outcome{true, 2, 100ms}));

  // 설정 파일을 다시 읽었다고 치고, 같은 Client의 전략을 실행 중에 바꾼다.
  client.set_retry(std::make_unique<ExponentialBackoff>(50ms, 400ms, 5));
  [[maybe_unused]] const Outcome after = simulate(2, run);
  assert((after == Outcome{true, 3, 150ms}));  // 50ms + 100ms
}

}  // namespace virt

fetch의 루프는 이제 재시도 규칙을 전혀 모릅니다. 새 규칙이 생기면 RetryStrategy를 상속한 클래스를 하나 더 만들면 됩니다. Client와 기존 전략은 고치지 않습니다.

소유권은 1편의 규칙대로 시그니처에 드러납니다. Client는 전략을 std::unique_ptr로 받아 소유합니다. const RetryStrategy&로 빌려 쓸 수도 있지만, 그러면 전략이 Client보다 오래 살아야 한다는 조건을 호출자가 지켜야 합니다.

구체 전략에 붙인 final도 의미가 있습니다. 컴파일러가 객체의 정확한 타입을 알 수 있는 곳에서는 가상 호출을 직접 호출로 바꿀 수 있습니다. 이를 비가상화(devirtualization)라고 합니다. 표준이 보장하는 최적화는 아니므로, 성능을 이것에 기대어 설계하지는 않습니다.

방법 2: std::function

전략 인터페이스에 함수가 하나뿐이라면, 클래스 계층 대신 "그 시그니처로 부를 수 있는 아무 값"을 받아도 됩니다. std::function은 호출 시그니처만 맞으면 함수 포인터·람다·함수 객체를 모두 담는 타입입니다. 담긴 값의 실제 타입은 지워집니다. 이 기법을 타입 소거(type erasure)라고 하며, 7편에서 직접 구현해 봅니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
namespace func {

using RetryFn = std::function<std::optional<Millis>(int failures)>;

RetryFn fixed_delay(Millis delay, int max_attempts) {
  return [=](int failures) -> std::optional<Millis> {
    if (failures >= max_attempts) return std::nullopt;
    return delay;
  };
}

RetryFn exponential_backoff(Millis initial, Millis cap, int max_attempts) {
  return [=](int failures) -> std::optional<Millis> {
    if (failures >= max_attempts) return std::nullopt;
    return capped_backoff(initial, cap, failures);
  };
}

class Client {
 public:
  explicit Client(RetryFn retry) : retry_(std::move(retry)) { assert(retry_); }

  bool fetch(FlakyService& svc, FakeClock& clock) const {
    for (int failures = 0;;) {
      if (svc.call()) return true;
      const std::optional<Millis> delay = retry_(++failures);
      if (!delay) return false;
      clock.sleep_for(*delay);
    }
  }

 private:
  RetryFn retry_;
};

void demo_shared_state() {
  // 즉석 정책: 전체 대기 예산 300ms를 다 쓰면 그만둔다. 남은 예산이 람다의 상태다.
  const Client client{[budget = Millis{300}](int) mutable -> std::optional<Millis> {
    if (budget < 100ms) return std::nullopt;
    budget -= 100ms;
    return 100ms;
  }};
  auto run = [&client](FlakyService& s, FakeClock& c) { return client.fetch(s, c); };

  [[maybe_unused]] const Outcome first = simulate(10, run);
  assert((first == Outcome{false, 4, 300ms}));  // 100ms씩 세 번 기다리고 예산이 바닥났다

  // const Client인데도 람다의 예산이 줄어든 채로 남아 있다. 두 번째 fetch는 첫 실패에서 바로 포기한다.
  [[maybe_unused]] const Outcome second = simulate(10, run);
  assert((second == Outcome{false, 1, 0ms}));
}

}  // namespace func

전략을 만드는 코드가 클래스 정의에서 람다 하나로 줄었습니다. 즉석에서 새 규칙을 만들기도 쉽습니다. demo_shared_state처럼 상태를 가진 규칙도 람다 캡처로 바로 만들 수 있습니다.

그런데 이 예제의 두 번째 fetch는 아마 의도한 동작이 아닐 것입니다. client는 const이고 fetch도 const 멤버 함수입니다. 그런데도 안에 담긴 람다의 budget이 바뀌었습니다. std::function::operator()는 const로 선언되어 있지만, 담긴 대상을 const가 아닌 값으로 부르기 때문입니다. 이것은 오래 알려진 std::function의 const 정확성(const-correctness) 구멍입니다. 상태가 있는 전략은 "호출마다 새로 시작해야 하는가, 이어져야 하는가"를 먼저 정해야 합니다. 이 구멍을 타입으로 막는 방법은 뒤의 「현대 C++ 대안」에서 봅니다.

방법 3: 템플릿 정책

앞의 두 방식은 전략을 실행 중(런타임)에 고릅니다. 하지만 캐시 서버용 클라이언트가 실행 중에 결제 API 규칙으로 바뀔 일은 없습니다. 이렇게 전략이 빌드할 때 정해진다면, 전략을 템플릿 인자로 받을 수 있습니다.

Andrei Alexandrescu는 이 방식을 정책 기반 설계(policy-based design)라고 불렀습니다. 클래스를 서로 독립적인 여러 정책(policy)의 조합으로 만듭니다. 여기서는 재시도 정책에 로그 정책을 하나 더 붙여 보겠습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
namespace policy {

// 정책은 기반 클래스가 필요 없다. 같은 이름의 멤버 함수만 있으면 된다.
struct FixedDelay {
  Millis delay;
  int max_attempts;
  std::optional<Millis> next_delay(int failures) const {
    if (failures >= max_attempts) return std::nullopt;
    return delay;
  }
};

struct ExponentialBackoff {
  Millis initial;
  Millis cap;
  int max_attempts;
  std::optional<Millis> next_delay(int failures) const {
    if (failures >= max_attempts) return std::nullopt;
    return capped_backoff(initial, cap, failures);
  }
};

// 로그 정책: 다시 시도하기 직전에 불린다. 기본값은 아무것도 하지 않는다.
struct NoLog {
  void on_retry(int /*failures*/, Millis /*delay*/) const noexcept {}
};

template <class Retry, class Log = NoLog>
class Client {
 public:
  explicit Client(Retry retry, Log log = Log{}) : retry_(std::move(retry)), log_(std::move(log)) {}

  bool fetch(FlakyService& svc, FakeClock& clock) {
    for (int failures = 0;;) {
      if (svc.call()) return true;
      const std::optional<Millis> delay = retry_.next_delay(++failures);
      if (!delay) return false;
      log_.on_retry(failures, *delay);
      clock.sleep_for(*delay);
    }
  }

  const Log& log() const noexcept { return log_; }

 private:
  Retry retry_;
  [[no_unique_address]] Log log_;  // 빈 정책은 자리를 차지하지 않는다(C++20)
};

// 로그 정책을 붙이지 않은 Client는 재시도 정책만큼의 크기다(g++ 14·clang 18에서 확인).
static_assert(sizeof(Client<FixedDelay>) == sizeof(FixedDelay));

// 테스트용 로그 정책: 기다린 시간을 기록한다.
struct RecordingLog {
  std::vector<Millis> delays;
  void on_retry(int /*failures*/, Millis delay) { delays.push_back(delay); }
};

void demo_log_policy() {
  Client client{ExponentialBackoff{100ms, 400ms, 5}, RecordingLog{}};
  FlakyService svc(10);
  FakeClock clock;
  [[maybe_unused]] const bool ok = client.fetch(svc, clock);
  assert(!ok);
  assert((client.log().delays == std::vector<Millis>{100ms, 200ms, 400ms, 400ms}));
}

}  // namespace policy

Client<ExponentialBackoff, RecordingLog>는 컴파일할 때 완전히 정해진 타입입니다. retry_.next_delay는 가상 호출이 아니라 보통의 멤버 함수 호출이므로 인라인될 수 있습니다. 정책은 기반 클래스를 상속할 필요가 없습니다. next_delay라는 이름과 맞는 시그니처만 있으면 됩니다.

[[no_unique_address]]는 C++20 속성입니다. 빈 타입 멤버가 다른 멤버와 주소를 겹쳐 써서 크기를 차지하지 않게 허용합니다. 그래서 NoLog를 붙여도 Client가 커지지 않습니다(static_assert로 확인). 다만 표준은 이것을 허용할 뿐 강제하지 않으며, 실제 배치는 ABI가 정합니다. 예를 들어 MSVC는 ABI 호환을 위해 표준 속성을 무시하고 [[msvc::no_unique_address]]만 적용하므로, MSVC에서는 위 static_assert가 실패합니다.

이 방식의 약점은 Client<FixedDelay>와 Client<ExponentialBackoff>가 서로 다른 타입이라는 점입니다. 둘을 한 std::vector에 넣을 수 없고, 실행 중에 정책을 바꿀 수도 없습니다. 이 차이는 트레이드오프 절에서 정리합니다.

세 구현을 같은 테스트로

세 구현이 같은 동작을 하는지 하나의 테스트로 확인합니다. 테스트는 "서비스와 시계를 받아 성공 여부를 돌려주는 함수" 두 개를 받습니다. 하나는 고정 간격(100ms, 최대 4회), 다른 하나는 지수 백오프(100ms부터 두 배, 상한 400ms, 최대 5회)입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
template <class RunFixed, class RunExp>
void check_retry(RunFixed fixed, RunExp exp) {
  [[maybe_unused]] const Outcome a = simulate(2, fixed);
  assert((a == Outcome{true, 3, 200ms}));  // 두 번 실패 → 100ms × 2 기다리고 세 번째에 성공

  [[maybe_unused]] const Outcome b = simulate(10, fixed);
  assert((b == Outcome{false, 4, 300ms}));  // 네 번 시도하고 포기. 대기는 시도 사이 세 번

  [[maybe_unused]] const Outcome c = simulate(3, exp);
  assert((c == Outcome{true, 4, 700ms}));  // 100 + 200 + 400

  [[maybe_unused]] const Outcome d = simulate(10, exp);
  assert((d == Outcome{false, 5, 1100ms}));  // 100 + 200 + 400 + 400(상한)

  [[maybe_unused]] const Outcome e = simulate(0, exp);
  assert((e == Outcome{true, 1, 0ms}));  // 첫 시도에 성공하면 기다리지 않는다
}

int main() {
  demo_naive();

  check_retry(
      [](FlakyService& s, FakeClock& c) {
        return virt::Client{std::make_unique<virt::FixedDelay>(100ms, 4)}.fetch(s, c);
      },
      [](FlakyService& s, FakeClock& c) {
        return virt::Client{std::make_unique<virt::ExponentialBackoff>(100ms, 400ms, 5)}.fetch(s, c);
      });

  check_retry(
      [](FlakyService& s, FakeClock& c) { return func::Client{func::fixed_delay(100ms, 4)}.fetch(s, c); },
      [](FlakyService& s, FakeClock& c) {
        return func::Client{func::exponential_backoff(100ms, 400ms, 5)}.fetch(s, c);
      });

  check_retry(
      [](FlakyService& s, FakeClock& c) { return policy::Client{policy::FixedDelay{100ms, 4}}.fetch(s, c); },
      [](FlakyService& s, FakeClock& c) {
        return policy::Client{policy::ExponentialBackoff{100ms, 400ms, 5}}.fetch(s, c);
      });

  virt::demo_swap();
  func::demo_shared_state();
  policy::demo_log_policy();
  std::puts("세 구현이 같은 테스트를 통과했습니다");
}

이 예제의 모든 assert는 실제로는 1초도 기다리지 않고 끝납니다. 시계를 바꿔 끼울 수 있게 만든 것 자체가 Strategy의 한 형태입니다. 이 예제에서는 시계를 함수 인자로 넘겼습니다. 정책 기반 설계라면 Client<Retry, Log, Clock>처럼 시계도 템플릿 인자로 받을 수 있습니다.

표준은 std::function이 작은 호출 대상을 힙 없이 저장하도록 권장만 합니다. 그 크기 기준은 표준 라이브러리마다 다릅니다. 이 글은 성능을 재지 않았으므로, 호출 비용이 중요한 코드라면 직접 측정한 뒤에 정하세요.

어느 방식이든 쓰지 말아야 할 때가 있습니다.

  • 알고리즘이 하나뿐이고 바뀔 계획도 없다면 Strategy를 만들지 않습니다. 함수 하나면 충분합니다. 바뀔 때 고쳐도 늦지 않습니다.
  • 정책이 설정 파일이나 사용자 입력으로 정해진다면 템플릿 정책은 맞지 않습니다. 결국 실행 중에 분기해야 하고, 가능한 조합마다 Client를 미리 인스턴스화해야 합니다.
  • 전략이 연산을 여러 개(예: next_delay와 reset) 가져야 한다면 std::function 하나로는 표현이 어색합니다. std::function 여러 개를 묶기보다 인터페이스를 만드는 편이 의도가 잘 드러납니다.
  • 상태를 가진 전략을 std::function에 담을 때는 위에서 본 const 구멍과, 복사하면 상태도 복사된다는 점을 함께 생각합니다. 공유해야 하는 상태라면 복사로 해결되지 않습니다.
  • 공개 라이브러리의 인터페이스에 템플릿 정책을 노출하면 정책을 바꿀 때마다 사용자 코드도 다시 컴파일해야 합니다. 바이너리 호환성이 중요한 경계에는 인터페이스 상속이 맞습니다(9편에서 다시 다룹니다).

현대 C++ 대안

현대 C++에서 Strategy 패턴은 두 방향으로 가벼워졌습니다. 런타임 쪽은 람다와 std::function 덕분에 클래스 계층이 필요 없어지는 경우가 많습니다. 컴파일 시점 쪽은 concept 덕분에 템플릿 정책의 요구 사항을 코드로 적을 수 있게 됐습니다.

C++20: concept으로 정책의 요구 사항 적기

앞의 policy::Client는 아무 타입이나 Retry로 받습니다. next_delay가 없는 타입을 넣으면 fetch 안쪽 깊은 곳에서 오류가 납니다. C++20의 concept을 쓰면 정책이 갖춰야 할 조건을 이름 붙여 적고, 조건을 어긴 타입은 선언 지점에서 거절할 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <chrono>
#include <concepts>
#include <optional>

using Millis = std::chrono::milliseconds;
using namespace std::chrono_literals;

// 재시도 정책의 요구 사항: 복사할 수 있고, const 객체에서 next_delay(int)를 불러
// 정확히 std::optional<Millis>를 돌려받을 수 있어야 한다.
template <class P>
concept RetryPolicy = std::copy_constructible<P> && requires(const P& p, int failures) {
  { p.next_delay(failures) } -> std::same_as<std::optional<Millis>>;
};

struct FixedDelay {
  Millis delay;
  int max_attempts;
  std::optional<Millis> next_delay(int failures) const {
    if (failures >= max_attempts) return std::nullopt;
    return delay;
  }
};

// 조건을 어기는 정책 두 가지
struct NonConstPolicy {  // next_delay가 const가 아니다: 호출마다 상태가 바뀔 수 있다
  std::optional<Millis> next_delay(int) { return std::nullopt; }
};
struct NeverGivesUp {  // 반환형이 optional이 아니다: "그만둔다"를 표현할 수 없다
  Millis next_delay(int) const { return 100ms; }
};

static_assert(RetryPolicy<FixedDelay>);
static_assert(!RetryPolicy<NonConstPolicy>);
static_assert(!RetryPolicy<NeverGivesUp>);

// 정책을 따라 시도할 때, 포기하기까지 기다리는 시간의 합
template <RetryPolicy Retry>
Millis total_wait_until_give_up(const Retry& retry) {
  Millis total{0};
  for (int failures = 1;; ++failures) {
    const std::optional<Millis> delay = retry.next_delay(failures);
    if (!delay) return total;
    total += *delay;
  }
}

int main() {
  [[maybe_unused]] const Millis total = total_wait_until_give_up(FixedDelay{100ms, 4});
  assert(total == 300ms);
}

requires 식 안의 { p.next_delay(failures) } -> std::same_as<…>는 "이 식이 컴파일되고, 결과 타입이 정확히 이것이어야 한다"는 뜻입니다. p를 const P&로 선언했으므로 const 멤버 함수만 조건을 만족합니다. same_as 대신 std::convertible_to를 쓰면 더 너그러운 조건이 됩니다. 예를 들어 next_delay가 Millis를 돌려줘도 optional로 변환되므로 통과합니다. 그러면 "그만둘 수 없는 정책"을 막지 못하므로, 여기서는 same_as를 골랐습니다.

조건을 어긴 정책을 넣으면 어떤 오류가 날까요?

cpp일부 발췌 · 검증 제외
total_wait_until_give_up(NeverGivesUp{});

g++ 14는 후보 함수를 보여 준 뒤, 어느 concept의 어느 요구 사항이 깨졌는지 짚습니다(경로와 일부 줄은 줄였습니다).

두 컴파일러 모두 "함수 본문 안에서 무엇이 실패했다"가 아니라 "이 타입은 RetryPolicy가 아니고, 깨진 조건은 반환형이다"라고 말합니다. 템플릿 정책의 요구 사항이 문서가 아니라 코드에 남습니다(Core Guidelines T.10).

C++17까지의 방법: enable_if

concept이 없던 C++17에서는 같은 조건을 타입 특성(type trait)과 std::enable_if로 적었습니다.

cpp일부 발췌 · 검증 제외
// C++17: 조건을 타입 특성으로 만들고, enable_if로 오버로드 후보에서 뺀다.
template <class P, class = void>
struct is_retry_policy : std::false_type {};

template <class P>
struct is_retry_policy<P, std::void_t<decltype(std::declval<const P&>().next_delay(0))>>
    : std::conjunction<
          std::is_copy_constructible<P>,
          std::is_same<decltype(std::declval<const P&>().next_delay(0)), std::optional<Millis>>> {};

template <class Retry, std::enable_if_t<is_retry_policy<Retry>::value, int> = 0>
Millis total_wait_until_give_up(const Retry& retry);

조건은 거의 같습니다. 복사 조건만 표준 concept std::copy_constructible 대신 그보다 느슨한 타입 특성 std::is_copy_constructible로 적었습니다. 그런데 읽기가 어렵습니다. 복사 조건처럼 하나를 빠뜨려도 컴파일은 그대로 되므로 실수를 알아채기도 어렵습니다. 조건이 함수 선언이 아니라 별도의 특성 클래스와 부분 특수화(partial specialization)에 흩어집니다. 오류 메시지도 조건의 내용까지는 알려 주지 못합니다. 같은 NeverGivesUp을 넣으면 g++ 14는 no type named 'type' in 'struct std::enable_if<false, int>'라고 합니다. clang 18은 requirement 'is_retry_policy<NeverGivesUp, void>::value' was not satisfied까지 알려 줍니다. 하지만 그 특성 안의 어느 조건(const 호출인지, 반환형인지)이 깨졌는지는 독자가 거꾸로 추적해야 합니다. 새 코드가 C++20을 쓸 수 있다면 concept을 고르지 않을 이유가 거의 없습니다.

C++23: std::move_only_function과 const 시그니처

std::function의 const 구멍은 C++23의 std::move_only_function이 타입으로 막습니다. 시그니처에 const를 붙일 수 있고, 그러면 const로 부를 수 없는 대상(예: mutable 람다)은 아예 담기지 않습니다. 이름처럼 이동만 가능하므로, std::unique_ptr처럼 복사할 수 없는 상태를 캡처한 전략도 담을 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++23)
#include <cassert>
#include <chrono>
#include <functional>
#include <memory>
#include <optional>
#include <type_traits>
#include <utility>

using Millis = std::chrono::milliseconds;
using namespace std::chrono_literals;

// 시그니처의 const: "이 전략은 const로 불러도 된다"는 약속을 타입이 검사한다.
using RetryFn = std::move_only_function<std::optional<Millis>(int failures) const>;

int main() {
  auto stateless = [](int failures) -> std::optional<Millis> {
    if (failures >= 4) return std::nullopt;
    return 100ms;
  };
  auto stateful = [budget = Millis{300}](int) mutable -> std::optional<Millis> {
    budget -= 100ms;
    return budget;
  };

  static_assert(std::is_constructible_v<RetryFn, decltype(stateless)>);
  static_assert(!std::is_constructible_v<RetryFn, decltype(stateful)>);  // mutable 람다는 거절된다
  // std::function은 둘 다 받아 준다.
  static_assert(std::is_constructible_v<std::function<std::optional<Millis>(int)>, decltype(stateful)>);

  // 복사할 수 없는 상태(unique_ptr)를 캡처한 전략도 담을 수 있다.
  RetryFn from_config = [limit = std::make_unique<int>(2)](int failures) -> std::optional<Millis> {
    if (failures >= *limit) return std::nullopt;
    return 50ms;
  };
  static_assert(!std::is_copy_constructible_v<RetryFn>);

  const RetryFn moved = std::move(from_config);
  assert(moved(1) == 50ms);
  assert(moved(2) == std::nullopt);
}

이 예제는 g++ 14와 clang 18(libstdc++ 14) 모두 -std=c++23에서 통과했습니다. std::move_only_function은 복사할 수 없으므로, 전략을 여러 객체에 복사해 나눠 주던 코드에는 그대로 바꿔 넣을 수 없습니다. 그런 코드라면 전략을 std::shared_ptr로 공유하거나, 상태 없는 전략으로 다시 설계합니다.

호출하는 동안만 빌려 쓰는, 소유하지 않는 호출 가능 참조 std::function_ref는 C++26 작업 초안에 채택됐습니다(P0792R14). 이 타입들의 내부 구조는 7편 Type Erasure에서 다룹니다.

정리

  • 먼저 바인딩 시점을 묻습니다. 실행 중에 전략을 바꿔야 하면 런타임 방식(인터페이스 상속 또는 std::function), 빌드할 때 정해지면 템플릿 정책이 맞습니다.
  • 전략이 연산 하나짜리이고 상태가 없으면 std::function(또는 C++23 std::move_only_function)과 람다로 충분합니다. 연산이 여럿이거나 라이브러리 경계를 넘어야 하면 인터페이스 상속을 씁니다.
  • 템플릿 정책은 직접 호출과 빈 정책 0바이트라는 이점이 있는 대신, 타입이 늘고 실행 중 교체가 안 됩니다. 요구 사항은 concept으로 적습니다.
  • 상태를 가진 전략은 "호출 사이에 상태가 이어지는가"를 먼저 정합니다. std::function의 const는 이것을 지켜 주지 않습니다.
  • 재시도·시계처럼 바뀌는 부분을 주입할 수 있게 만들면, 실제로 기다리지 않는 테스트를 쓸 수 있습니다.

다음 편에서는 상태 변화를 여러 객체에 알리는 Observer 패턴을 다룹니다. 관찰자가 먼저 사라지는 수명 문제를 std::weak_ptr와 RAII 연결 토큰으로 푸는 방법을 봅니다.
