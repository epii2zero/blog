Pimpl과 ABI 안정성 — 구현을 헤더 밖으로

private 멤버 하나를 바꿔도 사용하는 쪽 전체가 다시 컴파일되고 옛 바이너리와 객체 크기가 어긋나는 문제를 Pimpl로 풉니다. unique_ptr<Impl>이 불완전 타입에서 컴파일되지 않는 이유, 특수 멤버 함수를 구현 파일로 옮기는 규칙, shared_ptr·fast Pimpl·inline namespace를 비교하고 Pimpl이 지켜 주지 못하는 ABI 변경을 정리합니다.

8편은 "다음 편에서는 구현을 헤더 밖으로 숨겨 컴파일 의존을 끊는 Pimpl을 다룹니다"로 끝났습니다. 컴파일 의존을 끊으면 따라오는 효과가 하나 있습니다. 라이브러리를 새로 빌드해도, 그 라이브러리를 쓰는 옛 실행 파일이 그대로 동작할 수 있게 됩니다.

컴파일된 코드끼리 맞춰야 하는 약속(객체 크기와 멤버 위치, 함수 이름이 링커 심볼로 바뀌는 규칙인 맹글링(name mangling), 가상 함수 표의 배치 등)을 ABI(Application Binary Interface, 바이너리 인터페이스)라고 합니다. 소스 코드끼리의 약속인 API와 구분됩니다. Pimpl(pointer to implementation)은 클래스의 데이터 멤버를 구현 파일 안의 구조체로 옮기고, 클래스에는 그 구조체를 가리키는 포인터 하나만 남기는 기법입니다.

문제 상황

통계 라이브러리 하나를 배포한다고 해 봅시다.

  • 공개 헤더 stats.h에 Stats 클래스가 있습니다. 값을 더하고, 개수와 평균을 돌려줍니다.
  • 다음 버전에서 분산을 더하려고 합니다. 그러려면 제곱의 합을 저장할 private 멤버가 하나 늘어야 합니다.
  • 이 헤더를 포함한 파일은 수백 개이고, 라이브러리는 공유 라이브러리(.so)로 배포됩니다. 옛 버전으로 빌드한 프로그램이 새 .so와 함께 실행될 수 있습니다.

순진한 구현

데이터 멤버를 헤더의 클래스 정의에 그대로 둡니다. 두 버전을 이름공간 두 개로 나란히 놓고 비교해 보겠습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <initializer_list>

namespace v1 {
class Stats {
 public:
  void add(double x) { ++n_; sum_ += x; }
  std::size_t count() const { return n_; }
  double mean() const { return n_ ? sum_ / static_cast<double>(n_) : 0.0; }

 private:
  std::size_t n_ = 0;
  double sum_ = 0.0;
};
}  // namespace v1

namespace v2 {
class Stats {
 public:
  void add(double x) { ++n_; sum_ += x; sum_sq_ += x * x; }
  std::size_t count() const { return n_; }
  double mean() const { return n_ ? sum_ / static_cast<double>(n_) : 0.0; }
  double variance() const {
    if (n_ == 0) return 0.0;
    const double m = mean();
    return sum_sq_ / static_cast<double>(n_) - m * m;
  }

 private:
  std::size_t n_ = 0;
  double sum_ = 0.0;
  double sum_sq_ = 0.0;  // v2에서 추가한 private 멤버
};
}  // namespace v2

// private 멤버 하나가 객체 크기를 바꾼다
static_assert(sizeof(v2::Stats) > sizeof(v1::Stats));

int main() {
  v2::Stats s;
  for (double x : {1.0, 2.0, 3.0}) s.add(x);
  assert(s.count() == 3);
  assert(s.mean() == 2.0);
  assert(s.variance() > 0.66 && s.variance() < 0.67);  // 2/3
}

double 멤버를 하나 더했으므로 패딩으로 흡수되지 않고 크기가 늘어납니다. 바뀐 것은 private 멤버뿐인데 두 가지 일이 생깁니다.

  • 다시 컴파일: stats.h를 포함한 모든 파일이 다시 컴파일됩니다. 사용하는 쪽이 sum_sq_를 쓰지 않아도 마찬가지입니다.
  • 옛 바이너리: 위 예는 짧게 쓰려고 모든 함수를 인라인으로 두었지만, 실제 라이브러리라면 add 같은 함수는 .so 안에 정의됩니다. v1로 빌드한 프로그램은 Stats를 v1 크기만큼만 스택에 잡으므로, 새 .so의 add가 sum_sq_를 쓰면 그 객체 뒤의 메모리를 덮습니다. 멤버를 중간에 넣거나 순서를 바꾸면 문제가 하나 더 생깁니다. 헤더의 인라인 함수(count, mean)는 호출하는 쪽 코드에 옛 멤버 위치를 박아 두었으므로 엉뚱한 값을 읽습니다.

두 번째 상황은 "옛 바이너리 + 새 라이브러리"를 함께 실행해야 생기므로, 이 글의 CI처럼 모든 파일을 한 번에 빌드하는 방식으로는 재현할 수 없습니다. 이 부분은 문장과 1차 자료로 설명하고, 코드로는 그 원인인 크기 변화까지만 보입니다.

패턴 적용

헤더: 선언만 남긴다

Pimpl에서 헤더에 남는 것은 공개 함수 선언과 포인터 하나입니다. Impl은 이름만 선언합니다. 정의가 없는 타입을 불완전 타입(incomplete type)이라고 합니다. 불완전 타입은 크기를 모르므로 객체를 만들거나 지울 수 없지만, 가리키는 포인터는 만들 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#pragma once
#include <cstddef>
#include <memory>

class Stats {
 public:
  Stats();
  ~Stats();
  Stats(const Stats& other);
  Stats& operator=(const Stats& other);
  Stats(Stats&& other) noexcept;
  Stats& operator=(Stats&& other) noexcept;

  void add(double x);
  std::size_t count() const;
  double mean() const;
  double variance() const;

 private:
  struct Impl;               // 선언만. 정의는 stats.cpp에
  Impl& impl();
  const Impl& impl() const;  // const 함수는 이쪽만 쓸 수 있다
  std::unique_ptr<Impl> impl_;
};

특수 멤버 함수 여섯 개를 모두 선언만 했습니다. 하나씩 이유가 있습니다.

소멸자를 헤더에서 정의하면 안 되는 이유

소멸자를 선언하지 않으면 컴파일러가 암묵적으로 선언하고, 쓰이는 곳(odr-use)에서 정의합니다. 그 정의는 unique_ptr<Impl>의 소멸자를 부르고, 그 안의 default_delete<Impl>::operator()가 delete를 합니다. 표준은 이 연산자에 "T가 완전한 타입이어야 한다"는 조건을 Mandates로 둡니다. Mandates 조건을 어기면 프로그램은 ill-formed(형식에 맞지 않음)입니다. 그래서 Stats를 쓰는 파일에서 Impl이 불완전하면 컴파일되지 않습니다.

cpp컴파일 오류 예시
#include <memory>

class Stats {
 public:
  Stats();  // 소멸자를 선언하지 않았다

 private:
  struct Impl;
  std::unique_ptr<Impl> impl_;
};

void use() {
  Stats s;  // 블록을 나갈 때 암묵적 소멸자가 필요하다 → 여기서 정의된다
}

g++ 14와 clang 18(둘 다 libstdc++ 사용)은 모두 unique_ptr.h 안의 static_assert(sizeof(_Tp)>0, ...)에서 멈추고, "invalid application of 'sizeof' to incomplete type 'Stats::Impl'"이라고 알립니다. 오류를 static_assert로 내는 것은 libstdc++의 구현 방식이고, 표준이 요구하는 것은 "ill-formed이므로 진단해야 한다"까지입니다.

생성자도 구현 파일로

소멸자만 .cpp로 옮기면 끝이 아닙니다. 표준에는 "delegating이 아닌 생성자는 모든 하위 객체의 소멸자를 잠재적으로 호출(potentially invoked)한다"는 규칙이 있습니다. 생성 도중 예외가 나면 이미 만든 멤버를 지워야 하기 때문입니다. 그래서 헤더에서 정의한 생성자도 ~unique_ptr<Impl>을 요구합니다. 이동 생성자를 클래스 안에서 = default하면, 소멸자를 따로 선언했고 noexcept를 붙였는데도 실패합니다.

cpp컴파일 오류 예시
#include <memory>
#include <utility>

class Stats {
 public:
  Stats();
  ~Stats();                            // 소멸자는 선언만 했다
  Stats(Stats&&) noexcept = default;   // 이동 생성자를 클래스 안에서 정의

 private:
  struct Impl;
  std::unique_ptr<Impl> impl_;
};

void use(Stats& a) {
  Stats b(std::move(a));  // 이동 생성자가 쓰여 정의된다 → 멤버 소멸자가 필요
}

오류 문구는 앞의 예와 같고, 이번에는 이동 생성자 정의에서 시작합니다. 소멸자를 선언했으니 원인은 생성자 하나입니다. 기본 생성자를 클래스 안에서 = default해도 같은 규칙으로 실패합니다. 그래서 생성자·소멸자·대입 연산자는 모두 Impl이 정의된 .cpp에서 정의합니다.

이동 연산을 직접 선언하는 이유

소멸자를 선언하면 다른 문제가 하나 더 생깁니다. 사용자가 선언한 소멸자나 복사 연산이 있으면 컴파일러는 이동 생성자와 이동 대입을 암묵적으로 선언하지 않습니다. 이때 복사 연산이 있으면 std::move(s)는 오류 없이 복사로 처리됩니다. 깊은 복사를 하는 Pimpl에서는 이동할 때마다 힙 할당이 한 번씩 몰래 생깁니다. 그래서 이동 연산도 선언하고 .cpp에서 = default로 정의합니다.

구현 파일

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include "stats.h"

#include <cassert>

struct Stats::Impl {
  std::size_t n = 0;
  double sum = 0.0;
  double sum_sq = 0.0;  // 다음 버전에서 멤버를 더해도 헤더는 그대로
};

Stats::Stats() : impl_(std::make_unique<Impl>()) {}
Stats::~Stats() = default;  // 여기서는 Impl이 완전한 타입

// 이동된 객체(impl_ == nullptr)를 복사하면 결과도 이동된 상태(사전 조건에서 허용)
Stats::Stats(const Stats& other)
    : impl_(other.impl_ ? std::make_unique<Impl>(*other.impl_) : nullptr) {}

Stats& Stats::operator=(const Stats& other) {
  Stats copy(other);        // 먼저 복사하고
  impl_.swap(copy.impl_);   // 성공하면 바꾼다. 자기 대입도 안전하다
  return *this;
}

Stats::Stats(Stats&&) noexcept = default;
Stats& Stats::operator=(Stats&&) noexcept = default;

Stats::Impl& Stats::impl() {
  assert(impl_ && "이동된 Stats는 대입받기·소멸·복사와 이동의 원본으로만 쓸 수 있다");
  return *impl_;
}
const Stats::Impl& Stats::impl() const {
  assert(impl_ && "이동된 Stats는 대입받기·소멸·복사와 이동의 원본으로만 쓸 수 있다");
  return *impl_;
}

void Stats::add(double x) {
  Impl& d = impl();
  ++d.n;
  d.sum += x;
  d.sum_sq += x * x;
}
std::size_t Stats::count() const { return impl().n; }
double Stats::mean() const {
  const Impl& d = impl();
  return d.n ? d.sum / static_cast<double>(d.n) : 0.0;
}
double Stats::variance() const {
  const Impl& d = impl();
  if (d.n == 0) return 0.0;
  const double m = d.sum / static_cast<double>(d.n);
  return d.sum_sq / static_cast<double>(d.n) - m * m;
}

이동 뒤 impl_은 null입니다. 그래서 이 클래스는 "이동된 객체는 대입받기, 소멸, 복사·이동의 원본으로만 쓸 수 있다"는 사전 조건을 둡니다. 멤버 함수 호출은 허용하지 않습니다. impl()의 assert는 디버그 빌드에서 이 조건을 어긴 호출을 잡습니다. 복사 대입은 복사본을 먼저 만들고 포인터만 바꿉니다(copy-and-swap). 복사 중 예외가 나도 원래 객체는 그대로이고, 자기 대입도 따로 검사할 필요가 없습니다.

사용하는 쪽

main.cpp는 Impl의 정의를 볼 수 없습니다. 전역 operator new를 바꿔 끼워 힙 할당 횟수도 셉니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <cstdlib>
#include <initializer_list>
#include <new>
#include <utility>

#include "stats.h"

namespace {
int g_news = 0;  // operator new 호출 수
}
void* operator new(std::size_t n) {
  ++g_news;
  if (void* p = std::malloc(n ? n : 1)) return p;
  throw std::bad_alloc{};
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

// Impl을 몰라도 크기가 정해진다. 포인터 하나 크기는 흔한 구현의 결과일 뿐 표준 보장은 아니다
static_assert(sizeof(Stats) == sizeof(void*));

int main() {
  g_news = 0;
  Stats a;
  assert(g_news == 1);  // 생성: Impl 할당 1회
  for (double x : {1.0, 2.0, 3.0}) a.add(x);
  assert(a.count() == 3 && a.mean() == 2.0);

  Stats b = a;          // 깊은 복사
  assert(g_news == 2);
  b.add(10.0);
  assert(a.count() == 3 && b.count() == 4);  // 원본은 그대로

  Stats& alias = a;
  a = alias;            // 자기 대입
  assert(a.count() == 3);

  g_news = 0;
  Stats c = std::move(b);  // 이동: 할당 없음
  assert(g_news == 0 && c.count() == 4);

  b = a;                // 이동된 객체에 대입하면 다시 쓸 수 있다
  assert(b.count() == 3);

  Stats d = std::move(c);
  Stats e = c;          // 이동된 객체의 복사본도 이동된 상태
  e = d;
  assert(e.count() == 4);
}

const 전파

unique_ptr의 operator->는 const 멤버 함수이면서 const가 붙지 않은 T*를 돌려줍니다. 그래서 impl_->n = 0처럼 포인터를 직접 쓰면 const 멤버 함수 안에서도 Impl을 고칠 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <memory>
#include <type_traits>
#include <utility>

struct Impl { int n = 1; };

// const unique_ptr에서도 operator->는 const가 없는 포인터를 준다
static_assert(std::is_same_v<
    decltype(std::declval<const std::unique_ptr<Impl>&>().operator->()), Impl*>);

class Holder {
 public:
  void reset() const { impl_->n = 0; }  // const 함수인데 컴파일된다
  int value() const { return impl_->n; }

 private:
  std::unique_ptr<Impl> impl_ = std::make_unique<Impl>();
};

int main() {
  const Holder h;
  h.reset();
  return h.value();  // 0: const 객체의 상태가 바뀌었다
}

앞의 Stats는 impl()과 impl() const 두 접근자로 이 구멍을 막았습니다. const 멤버 함수에서는 const Impl&만 얻을 수 있으므로 수정은 컴파일 오류가 됩니다.

cpp컴파일 오류 예시
#include <memory>

class Stats {
 public:
  void reset() const { impl().n = 0; }  // const 함수에서 수정 시도

 private:
  struct Impl { int n = 0; };
  Impl& impl() { return *impl_; }
  const Impl& impl() const { return *impl_; }
  std::unique_ptr<Impl> impl_;
};

g++는 "assignment of member 'Stats::Impl::n' in read-only object", clang은 "cannot assign to return value because function 'impl' returns a const value"라고 알립니다. 같은 일을 하는 래퍼로 std::experimental::propagate_const가 있지만, 이것은 Library Fundamentals TS v2의 기능이고 표준이 아닙니다.

트레이드오프

비교 대상은 다섯 가지입니다. 추상 인터페이스 + 팩토리는 5편의 방식으로, 헤더에는 순수 가상 함수만 두고 객체는 팩토리 함수가 만듭니다. shared_ptr와 fast Pimpl은 다음 절에서 코드로 보입니다. "측정"이라고 적은 행의 숫자는 이 글의 코드가 assert로 확인한 값입니다. "구조상"이라고 적은 칸과 나머지 행은 코드 구조에서 나오는 사실이고, 따로 측정하지 않았습니다.

Pimpl이 지켜 주는 것과 못 지켜 주는 것

지켜 주는 것은 하나입니다. private 데이터 멤버를 더하거나 바꿔도 클래스의 크기와 멤버 배치, 헤더의 인라인 코드가 그대로입니다. 앞의 static_assert가 보인 내용입니다.

다음 변경은 Pimpl을 써도 바이너리 호환성을 깹니다.

  • 공개 함수의 시그니처 변경(매개변수, 반환 타입, const 여부). 맹글링된 심볼 이름이 바뀝니다.
  • 가상 함수 추가·순서 변경. 가상 함수 표의 배치가 바뀝니다.
  • 헤더에 남은 인라인 함수와 템플릿의 변경. 이 코드는 이미 사용하는 쪽에 컴파일되어 있습니다.
  • 컴파일러나 표준 라이브러리의 ABI 차이. 예를 들어 libstdc++는 GCC 5.1에서 std::string과 std::list의 새 구현을 넣으면서 옛 구현을 함께 남겼습니다(dual ABI).

현대 C++ 대안

shared_ptr<Impl>: 소멸자를 밖에 두지 않아도 된다

shared_ptr는 만들 때 삭제 방법을 제어 블록에 함께 담습니다. 그래서 Impl이 불완전한 헤더에서 암묵적 소멸자가 정의되어도 컴파일됩니다. 대신 make_shared<Impl>()은 Impl이 완전한 구현 파일에서 해야 합니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#pragma once
#include <cstddef>
#include <memory>

class SharedStats {
 public:
  SharedStats();  // 생성자는 구현 파일에. 소멸자·복사·이동은 암묵적으로
  void add(double x);
  std::size_t count() const;

 private:
  struct Impl;
  std::shared_ptr<Impl> impl_;
};
cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include "shared_stats.h"

struct SharedStats::Impl {
  std::size_t n = 0;
};

SharedStats::SharedStats() : impl_(std::make_shared<Impl>()) {}
void SharedStats::add(double) { ++impl_->n; }
std::size_t SharedStats::count() const { return impl_->n; }
cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <cstdlib>
#include <new>

#include "shared_stats.h"

namespace {
int g_news = 0;
}
void* operator new(std::size_t n) {
  ++g_news;
  if (void* p = std::malloc(n ? n : 1)) return p;
  throw std::bad_alloc{};
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

int main() {
  g_news = 0;
  SharedStats a;
  assert(g_news == 1);  // make_shared: 제어 블록과 Impl을 한 번에(표준 권고)
  SharedStats b = a;    // 기본 복사
  assert(g_news == 1);
  b.add(1.0);
  assert(a.count() == 1);  // 복사본을 고쳤는데 원본도 바뀌었다
}

비용은 원자적 참조 계수와 공유 의미입니다. 값처럼 복사하는 클래스라면 기본 복사가 얕은 공유가 되는 것이 버그의 원인이 됩니다. 불변 객체이거나 일부러 공유하려는 경우에만 맞습니다.

fast Pimpl: 힙 대신 고정 크기 버퍼

할당을 없애고 싶으면 객체 안에 정렬된 바이트 버퍼를 두고, 구현 파일에서 그 자리에 Impl을 만듭니다(placement new). C++23에서 deprecated된 std::aligned_storage 대신 alignas와 std::byte 배열을 씁니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#pragma once
#include <cstddef>

class FastStats {
 public:
  FastStats();
  ~FastStats();
  FastStats(const FastStats& other);
  FastStats& operator=(const FastStats& other);
  // 이동 연산은 선언하지 않았다 → std::move도 복사가 된다(여기서는 할당이 없어 괜찮다)

  void add(double x);
  std::size_t count() const;
  double mean() const;

 private:
  struct Impl;
  Impl& impl() noexcept;
  const Impl& impl() const noexcept;

  static constexpr std::size_t kSize = 32;  // 바꾸면 ABI가 바뀐다
  static constexpr std::size_t kAlign = alignof(std::max_align_t);
  alignas(kAlign) std::byte storage_[kSize];
};
cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include "fast_stats.h"

#include <new>

struct FastStats::Impl {
  std::size_t n = 0;
  double sum = 0.0;
  double sum_sq = 0.0;
};

FastStats::FastStats() {
  static_assert(sizeof(Impl) <= kSize, "kSize를 늘리면 ABI가 바뀐다");
  static_assert(alignof(Impl) <= kAlign);
  ::new (static_cast<void*>(storage_)) Impl{};
}
FastStats::~FastStats() { impl().~Impl(); }
FastStats::FastStats(const FastStats& other) {
  ::new (static_cast<void*>(storage_)) Impl(other.impl());
}
FastStats& FastStats::operator=(const FastStats& other) {
  impl() = other.impl();
  return *this;
}

FastStats::Impl& FastStats::impl() noexcept {
  return *std::launder(reinterpret_cast<Impl*>(storage_));
}
const FastStats::Impl& FastStats::impl() const noexcept {
  return *std::launder(reinterpret_cast<const Impl*>(storage_));
}

void FastStats::add(double x) {
  Impl& d = impl();
  ++d.n;
  d.sum += x;
  d.sum_sq += x * x;
}
std::size_t FastStats::count() const { return impl().n; }
double FastStats::mean() const {
  const Impl& d = impl();
  return d.n ? d.sum / static_cast<double>(d.n) : 0.0;
}
cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <cstdlib>
#include <new>

#include "fast_stats.h"

namespace {
int g_news = 0;
}
void* operator new(std::size_t n) {
  ++g_news;
  if (void* p = std::malloc(n ? n : 1)) return p;
  throw std::bad_alloc{};
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

int main() {
  g_news = 0;
  FastStats a;
  a.add(1.0);
  a.add(3.0);
  FastStats b = a;
  b.add(5.0);
  FastStats c;
  c = a;                // 복사 대입
  assert(g_news == 0);  // 생성·복사 모두 힙을 쓰지 않는다
  assert(a.count() == 2 && a.mean() == 2.0);
  assert(b.count() == 3 && c.count() == 2);
}

할당은 없어졌지만 비용이 옮겨 왔습니다. 소멸자·복사·이동을 모두 직접 써야 하고, std::launder로 버퍼를 Impl로 읽어야 합니다. Impl의 크기는 플랫폼과 빌드 설정(디버그용 멤버 등)마다 다를 수 있어 kSize에 여유를 둡니다. 그 여유를 넘는 순간 kSize를 바꿔야 하고, 그것은 곧 ABI 변경입니다. static_assert 두 줄은 그 순간을 컴파일 오류로 알려 줍니다.

모듈은 컴파일 방화벽을 대신하지 못한다

C++20 모듈을 쓰면 헤더를 파일마다 다시 파싱하지 않고, 매크로가 새어 나가지도 않습니다. 하지만 내보낸 클래스의 정의는 private 멤버까지 모듈 인터페이스에 있어야 합니다. 사용하는 쪽이 객체 크기를 알아야 하기 때문입니다. 그래서 private 멤버를 바꾸면 인터페이스가 바뀌고, 대부분의 빌드 시스템은 그 모듈을 import한 파일을 다시 컴파일합니다. 객체 배치도 바뀌므로 ABI 문제도 그대로입니다. 모듈이 줄여 주는 것은 파싱 비용이고, Pimpl이 끊는 것은 의존 자체입니다.

inline namespace: 깨진 조합을 링크 오류로

호환되지 않는 변경을 피할 수 없을 때는 inline namespace로 버전을 이름에 넣습니다. inline namespace의 멤버는 바깥 이름공간의 멤버처럼 쓸 수 있습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <type_traits>

namespace statslib {
inline namespace v2 {
class Stats {
 public:
  void add(double x);  // 라이브러리 안에 정의되는 함수
  int count() const { return n_; }

 private:
  int n_ = 0;
};
}  // namespace v2

// 실제로는 라이브러리의 .cpp에 있다. 심볼 이름에 v2가 들어간다
void Stats::add(double) { ++n_; }
}  // namespace statslib

// 소스에서는 statslib::Stats로 쓰지만, 실제 타입은 statslib::v2::Stats다
static_assert(std::is_same_v<statslib::Stats, statslib::v2::Stats>);

int main() {
  statslib::Stats s;
  s.add(1.0);
  assert(s.count() == 1);
}

inline namespace가 호환성을 지켜 주지는 않습니다. 하는 일은 버전 이름을 심볼에 넣는 것입니다. 사용하는 코드는 그대로 statslib::Stats라고 쓰지만, 맹글링된 이름에는 v2가 들어갑니다. v1 헤더로 빌드한 코드는 라이브러리 안에 정의된 함수를 statslib::v1::Stats::add 같은 이름으로 찾습니다. v2만 들어 있는 라이브러리와 새로 빌드하면 링크 오류가 납니다. 이미 빌드된 옛 실행 파일을 새 .so와 함께 실행하면 동적 링커가 멈춥니다. 즉시 바인딩(-z now)이면 프로그램을 불러올 때, 지연 바인딩이면 그 함수를 처음 부를 때 "undefined symbol"이나 "symbol lookup error"로 실패합니다. 어느 쪽이든 메모리를 조용히 덮는 대신 이름 불일치로 멈춥니다. libstdc++의 dual ABI도 새 std::string을 inline namespace std::__cxx11 안에 두는 방식입니다.

C++26 std::indirect

C++26에는 std::indirect<T>가 들어갑니다(P3019R14). 힙에 둔 객체 하나를 소유하는 래퍼인데, unique_ptr과 달리 복사하면 깊은 복사를 하고, const 경로로 접근하면 const가 전파됩니다. T는 불완전 타입이어도 되므로 Pimpl 멤버로 쓸 수 있고, 깊은 복사를 직접 쓴 복사 연산의 본문과 접근자 쌍은 필요 없어집니다. 다만 소멸자에는 unique_ptr처럼 "T가 완전한 타입"이라는 조건이 있고 복사 생성자는 T가 복사 가능하기를 요구하므로, 특수 멤버 함수를 헤더에서 선언만 하고 .cpp에서 = default로 정의하는 규칙은 그대로입니다. 이동된 indirect는 값이 없는(valueless) 상태가 되고 valueless_after_move()로 확인할 수 있습니다. 앞에서 이동된 Stats에 둔 사전 조건과 같은 상태입니다. 이 글의 CI 컴파일러에는 아직 없어서 코드 블록은 넣지 않았습니다.

정리

  • private 멤버를 헤더에 두면, 그 멤버를 바꿀 때 사용하는 쪽 전체가 다시 컴파일되고 객체 크기가 옛 바이너리와 어긋납니다.
  • Pimpl은 데이터 멤버를 구현 파일의 Impl로 옮기고 포인터 하나만 남깁니다. 객체 크기와 헤더가 구현과 무관해집니다.
  • unique_ptr<Impl>을 쓰면 생성자·소멸자·대입 연산자를 모두 Impl이 완전한 구현 파일에서 정의합니다. 소멸자를 선언하면 이동 연산도 직접 선언합니다.
  • 이동된 객체의 사전 조건, 깊은 복사, const 전파는 직접 정합니다. C++26 std::indirect는 깊은 복사와 const 전파를 맡아 주지만, 특수 멤버를 .cpp에서 정의하는 규칙은 남습니다.
  • Pimpl은 데이터 멤버 변경만 지켜 줍니다. 공개 시그니처, 가상 함수, 헤더의 인라인 코드를 바꾸는 것은 여전히 ABI 변경입니다. 피할 수 없으면 inline namespace로 버전을 심볼에 넣어 링크 오류로 드러나게 합니다.

이 글로 「C++ 디자인 패턴」 시리즈를 마칩니다. 수명과 소유(1·3편)는 해제 순서를 주석과 규칙으로 지키는 대신 RAII와 weak_ptr 같은 타입으로 표현했습니다. 다형성(2·4·6·7·8편)은 상속이 꼭 필요하지 않으면 템플릿, std::variant, 타입을 지운 값으로 옮길 수 있었고, 그 선택은 타입 집합이 열려 있는지와 값으로 복사해야 하는지로 정했습니다. 의존 끊기(5·9편)는 호출하는 쪽이 구체 타입이나 구현을 몰라야 할 때 팩토리와 Pimpl로 경계를 만들었고, C++26 std::indirect처럼 그 경계를 만드는 수고를 표준 라이브러리가 줄여 가고 있습니다. 어느 묶음이든 언어 기능이 같은 일을 더 적은 약속으로 해 주면 그쪽을 골랐고, 패턴은 그 기능이 닿지 않는 경계에서 썼습니다.
