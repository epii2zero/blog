Observer — 수명 문제와 weak_ptr

관찰자가 먼저 사라지거나 알림 도중 구독을 끊으면 Observer는 쉽게 깨집니다. 해제 후 사용과 재진입 문제를 짚고, RAII 구독 토큰과 weak_ptr 추적으로 수명이 안전한 Signal을 구현합니다. C++20 stop_callback과 멀티스레드 주의점도 다룹니다.

관찰자가 먼저 사라지거나, 알림을 받는 도중에 구독을 끊으면 무슨 일이 생길까요? Observer 패턴은 구조가 단순하지만, C++에서는 "누가 누구보다 오래 사는가"를 설계하지 않으면 해제된 객체를 부르게 됩니다. 이 글은 그 문제를 세 가지로 나눠 보고, RAII 구독 토큰과 std::weak_ptr로 수명이 안전한 Signal을 만듭니다. 다 읽고 나면 구독 API를 볼 때 "구독은 언제 끝나는가", "알림 도중에 목록이 바뀌면 어떻게 되는가"를 물을 수 있습니다.

문제 상황

설정 화면에서 글자 크기를 바꾸면 열려 있는 창들이 바로 반응해야 하는 편집기를 생각해 봅시다. 설정 객체는 창의 종류를 몰라야 합니다. 그래서 상태를 가진 쪽(주체, subject)이 변화를 알리고, 관심 있는 쪽(관찰자, observer)이 등록해 두었다가 알림을 받습니다. 이것이 GoF의 Observer 패턴입니다.

요구 사항은 다음과 같습니다.

  • 설정 객체는 프로그램이 끝날 때까지 살고, 미리보기 창은 수시로 열리고 닫힌다.
  • 창이 닫히면 알림이 끊겨야 한다. 해제 코드를 빠뜨려도 프로그램이 깨지면 안 된다.
  • 알림을 받은 창이 그 자리에서 자신을 닫거나 다른 창을 닫을 수 있다.
  • 드물지만 주체가 먼저 사라질 수도 있다. 남은 구독을 나중에 해제해도 안전해야 한다.

처음 두 항목은 수명 문제이고, 셋째는 재진입(reentrancy) 문제입니다. 재진입이란 어떤 함수가 실행되는 도중에 같은 객체의 함수가 다시 불리는 일입니다. 둘은 따로 해결해야 합니다.

순진한 구현

책에 나오는 구조를 그대로 옮기면 관찰자의 원시 포인터를 목록에 담게 됩니다. 원시 포인터는 1편의 규칙대로 "대여"를 뜻합니다. 문제는 대여 기간이 어디에도 적혀 있지 않다는 것입니다.

cpp일부 발췌 · 검증 제외
struct SettingsObserver {
  virtual ~SettingsObserver() = default;
  virtual void on_font_size(int pt) = 0;
};

class Settings {
 public:
  void attach(SettingsObserver* o) { observers_.push_back(o); }
  void detach(SettingsObserver* o) { std::erase(observers_, o); }
  void set_font_size(int pt) {
    for (SettingsObserver* o : observers_) o->on_font_size(pt);
  }

 private:
  std::vector<SettingsObserver*> observers_;  // 대여. 언제까지?
};

void broken(Settings& settings) {
  {
    auto dialog = std::make_unique<PreviewDialog>();
    settings.attach(dialog.get());
  }                            // 창은 사라졌지만 포인터는 목록에 남았다
  settings.set_font_size(14);  // 해제 후 사용(use-after-free)
}

첫째, 해제된 관찰자를 부른다

broken은 이미 해제된 객체를 부릅니다. 이런 오류를 해제 후 사용(use-after-free)이라고 하며, 미정의 동작(UB, undefined behavior)입니다. 이 코드를 g++ 14에서 ASan을 켜고 실행하면 다음과 같은 보고가 나옵니다(핵심 줄만 옮기고 주소는 줄였습니다).

text
ERROR: AddressSanitizer: heap-use-after-free on address 0x...
READ of size 8 at 0x... thread T0
    #0 in Settings::set_font_size(int)
    #1 in main
freed by thread T0 here:
    #1 in PreviewDialog::~PreviewDialog()

읽은 8바이트는 가상 함수 표를 가리키는 포인터입니다. 죽은 객체에서 이 포인터를 읽으므로, 운이 좋으면 멈추고 운이 나쁘면 엉뚱한 함수로 점프합니다.

기반 클래스의 소멸자에서 detach를 부르면 될 것 같지만, 구멍이 남습니다. 주체가 먼저 사라지면 이번에는 detach가 죽은 주체를 건드립니다. 기반 클래스의 소멸자는 파생 클래스의 멤버가 모두 파괴된 뒤에야 실행됩니다. 그래서 멤버를 파괴하는 동안 알림이 오면, 아직 해제되지 않은 구독이 이미 파괴된 멤버를 쓰는 재정의 함수를 부릅니다. 해제를 파생 클래스의 멤버가 맡아야 하는 이유입니다.

둘째, 알림 도중에 목록이 바뀐다

관찰자가 on_font_size 안에서 detach(this)를 부르면, 범위 기반 for가 돌고 있는 벡터에서 원소가 지워집니다. erase는 지운 위치와 그 뒤를 가리키는 반복자를 무효로 만들므로, 이것도 UB입니다. attach도 같습니다. 용량이 모자라 재할당이 일어나면 모든 반복자가 무효가 됩니다.

이 버그는 sanitizer로도 놓칠 수 있습니다. 관찰자 A·B·C가 있고 A가 자신을 지우는 코드를 이 글의 검증 환경에서 돌려 보면, 오류 없이 A C C가 출력됩니다. B는 빠지고 C는 두 번 불렸습니다. 벡터의 메모리 자체는 해제되지 않았으므로 ASan이 기본 설정으로는 알아채지 못합니다. libstdc++에서 -D_GLIBCXX_DEBUG(디버그 반복자)나 -D_GLIBCXX_SANITIZE_VECTOR(ASan 표시)를 켜면 두 옵션 모두 이 오류를 잡아냅니다.

반복자 대신 인덱스로 돌면 UB는 사라집니다. 그러나 버그는 남습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <functional>
#include <string>
#include <vector>

int main() {
  std::vector<std::function<void()>> observers;
  std::string log;
  observers.push_back([&] { log += 'A'; });
  observers.push_back([&] {
    log += 'B';
    observers.erase(observers.begin());  // 알림 도중에 앞의 A를 해제한다
  });
  observers.push_back([&] { log += 'C'; });

  for (std::size_t i = 0; i < observers.size(); ++i) {
    const auto callback = observers[i];  // 실행 중인 함수 객체가 지워지지 않도록 복사해 부른다
    callback();
  }
  assert(log == "AB");  // C는 한 칸 당겨져서 알림을 놓쳤다
}

목록 전체를 복사해 두고 복사본을 순회하는 방법도 흔합니다. 이 방법은 건너뛰기를 막습니다. 하지만 A가 B를 해제하고 파괴했을 때, 복사본에 남은 B가 그대로 불립니다. 다시 해제 후 사용입니다.

셋째, shared_ptr 목록은 관찰자를 붙잡는다

"수명이 문제라면 shared_ptr로 담자"는 생각도 자연스럽습니다. 해제 후 사용은 사라지지만, 이번에는 관찰자가 죽지 않습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <memory>
#include <vector>

struct PreviewDialog {
  explicit PreviewDialog(int& redraws) : redraws_(redraws) {}
  void on_font_size(int) { ++redraws_; }
  int& redraws_;
};

int main() {
  int redraws = 0;
  std::vector<std::shared_ptr<PreviewDialog>> observers;

  auto dialog = std::make_shared<PreviewDialog>(redraws);
  observers.push_back(dialog);
  dialog.reset();  // 사용자는 창을 닫았다고 생각한다

  for (const auto& o : observers) o->on_font_size(14);
  assert(redraws == 1);  // 닫은 창이 여전히 다시 그려진다
}

주체가 관찰자를 소유하게 된 것입니다. 명시적으로 해제하지 않으면 주체가 살아 있는 동안 관찰자도 살아 있습니다. 관찰자가 주체까지 shared_ptr로 쥐면 순환 참조가 되어 둘 다 영원히 해제되지 않습니다. 이렇게 잊힌 구독이 객체를 붙잡는 문제를 만료된 청취자(lapsed listener) 문제라고 부릅니다. 주체는 관찰자를 알아야 하지만 소유하면 안 됩니다.

패턴 적용

해결은 질문 세 개로 나눕니다.

  1. 구독은 언제 끝나는가? 구독을 자원으로 보고 1편의 RAII로 묶습니다. 토큰이 사라지면 구독도 끝납니다.
  2. 주체와 토큰 가운데 무엇이 먼저 사라져도 되는가? 서로 소유하지 않고 weak_ptr로만 가리킵니다.
  3. 알림 도중의 해제와 추가는 어떻게 되는가? 목록을 바로 줄이지 않고, 순회가 끝난 뒤에 정리합니다.

소유 관계를 그리면 다음과 같습니다. 실선은 소유, 점선은 관찰입니다.

text
Signal ──────▶ State ──────▶ Slot (콜백 + 연결 여부)
                 ▲              ▲
                 ┊ weak_ptr     ┊ weak_ptr
                 └┄┄┄ Connection ┄┘   ◀────── 관찰자가 멤버로 소유

Connection은 어느 쪽도 살려 두지 않습니다. Signal이 사라지면 State와 Slot이 해제되고, 토큰의 weak_ptr는 만료됩니다. 토큰이 먼저 사라지면 자기 Slot을 끊습니다.

구독 토큰 Connection

먼저 토큰과, 콜백 시그니처와 무관한 공통 부분입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <cstddef>
#include <functional>
#include <memory>
#include <optional>
#include <stdexcept>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

namespace detail {

struct SlotBase {
  bool connected = true;
};

struct StateBase {
  int depth = 0;  // 지금 진행 중인 emit의 중첩 깊이
  virtual void sweep() noexcept = 0;

 protected:
  ~StateBase() = default;  // StateBase*로 delete하지 않는다
};

}  // namespace detail

class [[nodiscard]] Connection {
 public:
  Connection() = default;
  Connection(std::weak_ptr<detail::StateBase> state, std::weak_ptr<detail::SlotBase> slot) noexcept
      : state_(std::move(state)), slot_(std::move(slot)) {}

  Connection(Connection&&) noexcept = default;
  Connection& operator=(Connection&& other) noexcept {
    if (this != &other) {
      disconnect();  // 쥐고 있던 구독부터 끝낸다
      state_ = std::move(other.state_);
      slot_ = std::move(other.slot_);
    }
    return *this;
  }
  ~Connection() { disconnect(); }

  void disconnect() noexcept {
    const auto state = std::exchange(state_, {}).lock();
    const auto slot = std::exchange(slot_, {}).lock();
    if (!slot) return;        // 이미 끊겼거나 Signal이 먼저 사라졌다
    slot->connected = false;  // 이 순간부터 불리지 않는다
    if (state && state->depth == 0) state->sweep();
  }

  bool connected() const noexcept {
    const auto slot = slot_.lock();
    return slot && slot->connected;
  }

 private:
  std::weak_ptr<detail::StateBase> state_;
  std::weak_ptr<detail::SlotBase> slot_;
};

이 클래스는 1편의 File과 모양이 같습니다. 복사는 안 되고 이동만 되며, 이동 대입은 쥐고 있던 자원을 먼저 놓습니다. 이동 연산을 선언했으므로 복사 연산은 자동으로 삭제됩니다. 이동된 weak_ptr는 비므로, 이동 뒤의 원본은 소멸해도 아무것도 끊지 않습니다.

[[nodiscard]]는 반환된 토큰을 버리는 실수를 막습니다. 토큰을 받지 않으면 그 문장이 끝나는 즉시 구독이 끊기기 때문입니다.

disconnect가 하는 일은 두 단계입니다. 먼저 connected를 내려서 더는 불리지 않게 합니다. 그리고 알림이 진행 중이 아닐 때(depth == 0)만 목록에서 지웁니다. 알림 도중에 목록을 건드리지 않는 것이 재진입 안전의 핵심입니다.

Signal

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
template <class... Args>
class Signal {
  struct Slot : detail::SlotBase {
    std::function<void(const Args&...)> fn;
    std::optional<std::weak_ptr<const void>> tracked;  // 값이 있으면 이 객체가 살아 있을 때만 부른다
  };

  struct State final : detail::StateBase {
    std::vector<std::shared_ptr<Slot>> slots;

    // 끊긴 슬롯을 지운다. depth가 0일 때만 부른다.
    void sweep() noexcept override {
      std::size_t kept = 0;
      for (auto& slot : slots) {
        if (!slot->connected) continue;
        slots[kept].swap(slot);  // 살아 있는 슬롯의 순서는 지키고, 끊긴 슬롯은 뒤로 보낸다
        ++kept;
      }
      while (!slots.empty() && !slots.back()->connected) {
        const auto dead = std::move(slots.back());
        slots.pop_back();
      }  // dead의 콜백은 pop_back이 끝난 뒤에 파괴된다
    }
  };

 public:
  Signal() : state_(std::make_shared<State>()) {}
  ~Signal() {
    for (auto& slot : state_->slots) slot->connected = false;
  }
  Signal(const Signal&) = delete;
  Signal& operator=(const Signal&) = delete;

  Connection connect(std::function<void(const Args&...)> fn) {
    assert(fn);  // 빈 콜백은 등록할 때 거른다
    auto slot = std::make_shared<Slot>();
    slot->fn = std::move(fn);
    return add(std::move(slot));
  }

  // 추적 구독: obj를 소유하지 않는다. 부르는 동안에만 살려 둔다.
  template <class T, class F>
  Connection connect(const std::shared_ptr<T>& obj, F f) {
    assert(obj);
    auto slot = std::make_shared<Slot>();
    slot->tracked = std::weak_ptr<const void>(obj);
    slot->fn = [raw = obj.get(), f = std::move(f)](const Args&... args) mutable { std::invoke(f, *raw, args...); };
    return add(std::move(slot));
  }

  void emit(Args... args) {
    const std::shared_ptr<State> state = state_;  // 알림 도중 Signal이 사라져도 State는 남는다
    struct DepthGuard {
      State& s;
      explicit DepthGuard(State& state_ref) noexcept : s(state_ref) { ++s.depth; }
      DepthGuard(const DepthGuard&) = delete;
      DepthGuard& operator=(const DepthGuard&) = delete;
      ~DepthGuard() {
        if (--s.depth == 0) s.sweep();
      }
    } guard(*state);

    const std::size_t count = state->slots.size();  // 알림 도중 추가된 구독은 다음 알림부터
    for (std::size_t i = 0; i < count; ++i) {
      Slot& slot = *state->slots[i];  // 순회 중에는 슬롯을 지우지 않으므로 유효하다
      if (!slot.connected) continue;
      std::shared_ptr<const void> alive;
      if (slot.tracked) {
        alive = slot.tracked->lock();
        if (!alive) {
          slot.connected = false;  // 대상이 사라졌다. 순회가 끝나면 정리한다
          continue;
        }
      }
      slot.fn(args...);
    }
  }

  std::size_t slot_count() const noexcept { return state_->slots.size(); }

 private:
  Connection add(std::shared_ptr<Slot> slot) {
    state_->slots.push_back(slot);
    return Connection{state_, slot};
  }

  std::shared_ptr<State> state_;
};

짧은 코드지만 결정이 많이 들어 있습니다.

  • 목록은 순회 중에 줄지 않습니다. 가장 바깥 emit이 끝날 때 DepthGuard의 소멸자가 한 번에 정리합니다. 콜백이 예외를 던져도 깊이가 되돌아갑니다. 이것도 RAII입니다.
  • 알림 도중 추가된 구독은 이번 알림을 받지 않습니다. 시작할 때 센 count까지만 돕니다.
  • 벡터는 인덱스로 순회합니다. push_back이 벡터를 재할당해도 인덱스는 유효합니다. Slot은 따로 할당된 객체이고 순회 중에는 지우지 않으므로, 실행 중인 콜백도 옮겨지거나 파괴되지 않습니다.
  • Signal이 알림 도중 사라져도 안전합니다. 지역 변수 state가 State를 붙잡고, Signal의 소멸자가 모든 슬롯을 끊습니다. 그래서 남은 콜백은 불리지 않습니다.
  • 인자는 값으로 받습니다. 주체의 멤버를 참조로 받으면, 콜백이 주체를 파괴했을 때 그 참조가 끊깁니다. 복사 한 번의 비용으로 이 문제를 없앱니다. 다만 Signal<const std::string&>처럼 참조를 템플릿 인자로 주면 다시 참조가 되므로, Signal<std::string>처럼 값 타입으로 씁니다.
  • 정리할 때 슬롯을 목록에서 먼저 뺍니다. 콜백이 파괴되면 캡처한 객체의 소멸자가 실행되고, 그 안에서 다시 disconnect나 connect가 불릴 수 있습니다. 목록이 정돈된 상태에서 파괴해야 합니다. 그 소멸자가 새 구독을 추가하면 남은 끊긴 슬롯은 다음 정리 때 지워집니다.

관찰자가 토큰을 멤버로 갖는다

가장 흔한 형태는 관찰자가 Connection을 멤버로 두는 것입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
class PreviewDialog {
 public:
  explicit PreviewDialog(Signal<int>& font_size_changed)
      : connection_(font_size_changed.connect([this](int pt) { last_pt_ = pt; })) {}

  // 람다가 this를 쥐었으므로 객체의 주소가 바뀌면 안 된다.
  PreviewDialog(PreviewDialog&&) = delete;
  PreviewDialog& operator=(PreviewDialog&&) = delete;

  int last_pt() const noexcept { return last_pt_; }

 private:
  int last_pt_ = 0;
  Connection connection_;  // 마지막에 선언한다: 가장 먼저 파괴된다
};

static_assert(!std::is_copy_constructible_v<Connection>);
static_assert(std::is_nothrow_move_constructible_v<Connection>);
static_assert(!std::is_move_constructible_v<PreviewDialog>);

void demo_member_token() {
  Signal<int> font_size_changed;
  {
    PreviewDialog dialog(font_size_changed);
    font_size_changed.emit(14);
    assert(dialog.last_pt() == 14);
    assert(font_size_changed.slot_count() == 1);
  }  // ~PreviewDialog → ~Connection → 구독 해제
  assert(font_size_changed.slot_count() == 0);
  font_size_changed.emit(16);  // 부를 대상이 없다
}

void demo_signal_dies_first() {
  auto signal = std::make_unique<Signal<int>>();
  Connection c = signal->connect([](int) {});
  assert(c.connected());
  signal.reset();  // 주체가 먼저 사라졌다
  assert(!c.connected());
}  // ~Connection은 만료된 weak_ptr를 보고 아무것도 하지 않는다

여기서 놓치기 쉬운 것이 두 가지 있습니다.

첫째, 멤버 선언 순서입니다. 멤버는 선언한 순서의 역순으로 파괴됩니다. connection_을 마지막에 두면 가장 먼저 파괴됩니다. 그러면 다른 멤버가 부서지는 동안 알림이 들어올 수 없습니다.

둘째, 이동입니다. Connection은 이동할 수 있으므로, 이동을 막지 않으면 PreviewDialog도 이동 가능한 타입이 됩니다. 그런데 람다 속 this는 옛 주소를 그대로 가리킵니다. 이동한 뒤의 알림은 옛 객체에 값을 씁니다. this를 캡처해 등록했다면 이동을 삭제하거나, 이동 생성자에서 다시 구독해야 합니다.

추적 구독: weak_ptr로 대상의 수명을 본다

관찰자를 이미 shared_ptr로 관리한다면 토큰 대신 대상의 수명을 직접 볼 수 있습니다. 두 번째 connect가 그 용도입니다. 알림 때마다 lock()을 시도해서, 성공하면 부르는 동안만 shared_ptr로 붙잡습니다. 실패하면 구독을 끊습니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
struct OutlinePanel {
  explicit OutlinePanel(int& redraws) : redraws_(redraws) {}
  void on_font_size(int) { ++redraws_; }
  int& redraws_;
};

void demo_tracked() {
  Signal<int> font_size_changed;
  int redraws = 0;

  auto panel = std::make_shared<OutlinePanel>(redraws);
  Connection c = font_size_changed.connect(panel, &OutlinePanel::on_font_size);
  assert(panel.use_count() == 1);  // Signal은 panel을 소유하지 않는다

  font_size_changed.emit(14);
  assert(redraws == 1);

  panel.reset();  // 토큰은 남았지만 대상이 사라졌다
  font_size_changed.emit(16);
  assert(redraws == 1);  // 불리지 않았고
  assert(!c.connected() && font_size_changed.slot_count() == 0);  // 슬롯도 정리됐다
}

void demo_destroyed_while_called() {
  Signal<int> changed;
  int redraws = 0;
  auto panel = std::make_shared<OutlinePanel>(redraws);
  const std::weak_ptr<OutlinePanel> watch = panel;
  Connection c = changed.connect(panel, [&](OutlinePanel& self, int pt) {
    panel.reset();             // 바깥의 마지막 소유자가 사라진다
    assert(!watch.expired());  // emit이 붙잡고 있다
    self.on_font_size(pt);
  });
  changed.emit(14);
  assert(redraws == 1 && watch.expired());  // 호출이 끝나자 파괴됐다
}

lock()이 하는 일이 중요합니다. expired()를 확인한 다음 원시 포인터로 부르면, 확인과 호출 사이(멀티스레드)나 호출 도중(한 스레드에서도)에 대상이 사라질 수 있습니다. lock()은 확인과 소유권 획득을 한 번에 합니다.

추적 구독에도 함정이 있습니다.

  • 콜백이 대상의 shared_ptr를 캡처하면 처음의 문제로 돌아갑니다. 슬롯이 대상을 붙잡아 만료되지 않습니다.
  • 생성자 안에서는 추적 구독을 할 수 없습니다. 생성자가 도는 동안에는 아직 이 객체를 소유한 shared_ptr가 없습니다. 이때 shared_from_this()를 부르면 std::bad_weak_ptr가 발생합니다. 객체를 만든 뒤 구독하는 팩토리 함수를 둡니다.
  • lock()은 shared_ptr가 정말 소유하는 대상만 지켜 줍니다. 다른 객체의 소유권을 빌린 별칭(aliasing) shared_ptr라면 대상이 이미 없을 수 있습니다.
  • std::make_shared로 만든 객체의 메모리는 보통 마지막 weak_ptr가 사라져야 반환됩니다. 알림이 드문 신호라면 만료를 발견할 다음 emit까지 남습니다.

재진입을 테스트로 확인한다

요구 사항의 셋째 항목을 확인합니다. 알림 도중의 자기 해제, 남의 해제, 구독 추가, 중첩 알림, 예외, 주체 파괴입니다. 마지막 테스트에서는 알림 도중 끊긴 구독을 바깥 emit이 정리할 때, 파괴되는 콜백의 캡처가 다시 해제를 부릅니다. 슬롯을 목록에서 빼지 않고 std::erase_if로 제자리에서 파괴하면 이 테스트가 실패합니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
void test_disconnect_during_emit() {
  Signal<int> s;
  std::string log;
  Connection a, b, c;
  a = s.connect([&](int) { log += 'A'; a.disconnect(); });  // 자기 해제
  b = s.connect([&](int) { log += 'B'; c.disconnect(); });  // 뒤에 있는 구독 해제
  c = s.connect([&](int) { log += 'C'; });
  s.emit(1);
  assert(log == "AB");  // A가 사라져도 B를 건너뛰지 않고, 끊긴 C는 불리지 않는다
  assert(s.slot_count() == 1);
  s.emit(2);
  assert(log == "ABB");
}

void test_connect_during_emit() {
  Signal<int> s;
  std::vector<Connection> added;
  int calls = 0;
  Connection c = s.connect([&](int) { added.push_back(s.connect([&](int) { ++calls; })); });
  s.emit(1);
  assert(calls == 0 && added.size() == 1);  // 이번 알림에는 끼지 않는다
  s.emit(2);
  assert(calls == 1 && added.size() == 2);
}

void test_nested_emit() {
  Signal<int> s;
  std::string log;
  Connection a, b;
  a = s.connect([&](int depth) {
    log += 'A';
    if (depth == 0) {
      s.emit(1);
      b.disconnect();
    }
  });
  b = s.connect([&](int) { log += 'B'; });
  s.emit(0);
  assert(log == "AAB");  // 안쪽 emit은 A, B를 부르고, 바깥 emit은 끊긴 B를 건너뛴다
  assert(s.slot_count() == 1);
}

void test_exception() {
  Signal<int> s;
  std::string log;
  Connection a = s.connect([&](int) {
    a.disconnect();
    throw std::runtime_error("관찰자 실패");
  });
  Connection b = s.connect([&](int) { log += 'B'; });
  [[maybe_unused]] bool caught = false;
  try {
    s.emit(1);
  } catch (const std::runtime_error&) {
    caught = true;
  }
  assert(caught && log.empty());  // 예외는 밖으로 나가고 뒤의 B는 불리지 않았다
  assert(s.slot_count() == 1);    // 그래도 A는 정리됐다
  s.emit(2);
  assert(log == "B");
}

void test_signal_destroyed_during_emit() {
  auto s = std::make_unique<Signal<int>>();
  std::string log;
  Connection a = s->connect([&](int) { log += 'A'; s.reset(); });  // 알림 도중 주체를 파괴한다
  Connection b = s->connect([&](int) { log += 'B'; });
  s->emit(1);
  assert(log == "A" && !s && !b.connected());
}

void test_capture_destroyed_in_sweep() {
  Signal<int> s;
  Connection inner = s.connect([](int) {});
  Connection tail = s.connect([](int) {});
  // a의 콜백이 inner의 토큰을 소유한다. 알림 도중 a를 끊으면 바깥 emit의 정리가
  // a의 콜백을 마지막으로 파괴하고, 그 소멸자가 다시 disconnect를 부른다.
  Connection a;
  a = s.connect([&a, held = std::make_shared<Connection>(std::move(inner))](int) { a.disconnect(); });
  assert(s.slot_count() == 3);
  s.emit(1);
  assert(s.slot_count() == 1 && tail.connected());
}

int main() {
  demo_member_token();
  demo_signal_dies_first();
  demo_tracked();
  demo_destroyed_while_called();
  test_disconnect_during_emit();
  test_connect_during_emit();
  test_nested_emit();
  test_exception();
  test_signal_destroyed_during_emit();
  test_capture_destroyed_in_sweep();
}

test_exception이 보여 주는 동작은 선택입니다. 여기서는 첫 예외를 그대로 내보내고 나머지 관찰자를 부르지 않습니다. 모두 부른 뒤 모아서 던지거나, 관찰자에게 noexcept를 요구할 수도 있습니다. 무엇을 고르든 문서에 적어야 합니다.

자기 파괴에는 아직 한계가 있습니다. 토큰을 멤버로 둔 관찰자가 자기 콜백 안에서 자신을 delete하면, Slot은 살아 있어도 this는 죽습니다. 콜백의 남은 코드가 멤버를 건드리면 UB입니다. 이런 관찰자에는 추적 구독이 맞습니다. 부르는 동안 대상을 붙잡아 주기 때문입니다.

트레이드오프

방식구독이 끝나는 때관찰자를 소유하는가주체가 먼저 사라지면추가 비용
원시 포인터 목록직접 detach할 때아니요detach가 UB없음
shared_ptr 목록직접 detach할 때예(만료된 청취자)detach가 UB(관찰자가 주체를 shared_ptr로 쥐면 순환)참조 횟수
RAII 토큰(Connection)토큰이 사라질 때아니요안전슬롯 할당, 토큰의 weak_ptr 2개
weak_ptr 추적대상이 만료될 때부르는 동안만안전위 비용 + 알림마다 lock()

RAII 토큰과 추적 구독의 선택 기준은 관찰자의 소유 방식입니다. 값이나 unique_ptr로 관리한다면 토큰이 맞습니다. 이미 shared_ptr로 공유한다면 추적을 더할 수 있습니다. 추적만을 위해 모든 관찰자를 shared_ptr로 바꿀 필요는 없습니다.

Observer 패턴을 쓰지 말아야 할 때도 있습니다.

  • 관찰자가 하나이고 컴파일할 때 정해진다면 콜백 하나를 생성자로 받거나 함수의 반환값으로 결과를 돌려주면 됩니다.
  • 두 객체의 수명이 같은 곳에서 정해진다면 참조 하나로 충분합니다. 예를 들어 두 객체가 한 클래스의 멤버라면, 파괴 순서가 코드에 이미 적혀 있습니다.
  • 알림이 알림을 부르는 사슬이 길어진다면 호출 흐름을 추적하기 어렵습니다. 변경을 모아 두었다가 이벤트 루프에서 한 번에 처리하는 큐가 낫습니다.
  • 알림 순서가 정확성을 좌우한다면 순서를 명시적인 함수 호출로 드러냅니다.

멀티스레드에서는 무엇이 달라지나

이 글의 Signal은 한 스레드에서만 쓰는 설계입니다. slots·connected·depth를 동기화 없이 읽고 씁니다. 글의 검증 환경에 ThreadSanitizer가 없으므로 스레드 안전한 구현은 싣지 않고, 주의점만 적습니다.

  • 잠금(lock)을 쥔 채 콜백을 부르면 안 됩니다. 콜백이 같은 신호에 다시 구독하면 교착 상태(deadlock)에 빠집니다(Core Guidelines CP.22).
  • 그래서 목록을 복사한 뒤 잠금을 풀고 부르게 됩니다. 이때 다른 스레드의 disconnect가 반환된 뒤에도 콜백이 아직 실행 중일 수 있습니다. 토큰만으로는 this를 지키지 못합니다.
  • 해결은 둘 중 하나입니다. disconnect가 실행 중인 콜백을 기다리거나(콜백 안에서 자신을 해제하는 경우는 예외로 둬야 합니다), 추적 구독처럼 호출 동안 대상을 붙잡습니다.
  • weak_ptr::lock()은 원자적으로 실행되므로, 서로 다른 weak_ptr 사본으로 불러도 경쟁이 없습니다. 하지만 대상의 멤버에 동시에 접근하는 문제는 따로 동기화해야 합니다.

현대 C++ 대안

C++20 std::stop_callback: 표준에 있는 RAII 구독

"한 번만 일어나는 사건"을 알리는 것이라면 표준 라이브러리에 이미 있습니다. std::stop_source가 주체, std::stop_token이 구독할 권리, std::stop_callback이 RAII 토큰입니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++20)
#include <cassert>
#include <stop_token>
#include <string>

int main() {
  std::stop_source source;  // 주체: "중단"이라는 한 번뿐인 사건
  std::string log;

  {
    std::stop_callback first(source.get_token(), [&] { log += 'A'; });
  }  // 등록 해제: 이 콜백은 불리지 않는다

  std::stop_callback second(source.get_token(), [&] { log += 'B'; });
  assert(log.empty());

  [[maybe_unused]] const bool first_request = source.request_stop();
  [[maybe_unused]] const bool second_request = source.request_stop();
  assert(first_request && !second_request);  // 사건은 한 번만 일어난다
  assert(log == "B");

  std::stop_callback late(source.get_token(), [&] { log += 'C'; });
  assert(log == "BC");  // 이미 일어난 사건이면 등록하는 자리에서 바로 부른다
}

이 설계는 앞 절의 멀티스레드 질문에도 답을 정해 두었습니다. stop_callback의 소멸자는 콜백이 다른 스레드에서 실행 중이면 끝날 때까지 기다립니다. 같은 스레드, 곧 콜백 안에서 파괴하면 기다리지 않고 반환합니다. 반면 콜백이 예외를 던지면 std::terminate가 불립니다. 값을 실어 보낼 수도 없고 반복할 수도 없으므로 Signal을 대신하지는 못합니다. 취소, 종료, 창 닫힘 같은 사건에 맞습니다.

C++23 std::move_only_function: 이동 전용 캡처

슬롯은 콜백을 복사할 일이 없습니다. 그런데 std::function은 담는 대상이 복사 가능하기를 요구합니다. 그래서 unique_ptr를 캡처한 람다는 connect에 넘길 수 없습니다. 2편에서 본 std::move_only_function으로 슬롯 타입을 바꾸면 이 제약이 사라집니다.

cpp컴파일 검증됨 (g++ 14.2 · clang 18.1, C++23)
#include <cassert>
#include <functional>
#include <memory>
#include <type_traits>
#include <utility>

int main() {
  int seen = 0;
  auto sink = std::make_unique<int*>(&seen);
  auto observer = [sink = std::move(sink)](const int& pt) { **sink = pt; };
  static_assert(!std::is_copy_constructible_v<decltype(observer)>);  // std::function에는 담을 수 없다

  std::move_only_function<void(const int&)> slot = std::move(observer);
  slot(14);
  assert(seen == 14);
}

이 글의 본문이 std::function을 쓴 이유는 C++20에서 컴파일되게 하려는 것입니다. 주의할 점이 하나 있습니다. 비어 있는 std::function을 부르면 std::bad_function_call이 발생하지만, 빈 move_only_function을 부르면 UB입니다. 본문의 connect가 빈 콜백을 assert로 먼저 거르는 것이 이 경우에는 더 중요해집니다.

C++26의 std::function_ref는 슬롯에 맞지 않습니다. 호출 대상을 소유하지 않는 참조이므로, 목록에 담아 두면 처음의 원시 포인터 문제가 되살아납니다.

본문의 Signal 예제는 C++17에서도 그대로 컴파일됩니다(g++ 14·clang 18에서 -std=c++17로 따로 확인).

정리

  • 주체는 관찰자를 알아야 하지만 소유하면 안 됩니다. 원시 포인터는 대여 기간을 표현하지 못하고, shared_ptr는 관찰자를 붙잡습니다.
  • 구독은 자원입니다. 토큰을 관찰자의 마지막 멤버로 두고, this를 캡처했다면 이동을 막습니다.
  • 관찰자가 이미 shared_ptr로 공유된다면 weak_ptr 추적을 씁니다. expired()가 아니라 lock()으로 확인하고, 부르는 동안 붙잡습니다.
  • 알림 도중에는 표시만 하고 정리는 순회 뒤로 미룹니다. 추가·중첩·예외·주체 파괴의 규칙을 정해 문서와 테스트로 남깁니다.
  • 한 번뿐인 사건이면 std::stop_callback을 먼저 봅니다. 관찰자가 하나이거나 수명이 같으면 패턴 없이 콜백이나 참조로 충분합니다.

다음 편에서는 가상 함수 없이 공통 동작을 물려주는 CRTP와, C++23의 deducing this가 그 자리를 얼마나 대신하는지 살펴봅니다.
