TL;DR: 요즘 AI 에이전트는 검색, 코드 실행, 파일 읽기를 수십~수백 번 반복하며 일한다. 그런데 일이 길어질수록 지나온 기록을 계속 들고 다니는 비용이 눈덩이처럼 불어난다. 지금까지는 오래된 기록을 요약하거나 잘라내는 방식(컨텍스트 엔지니어링)으로 대응했는데, 기록을 고치는 순간 그 뒤의 계산을 처음부터 다시 해야 하고, 요약 과정에서 중요한 정보도 빠진다. 칭화대 연구진은 기록(텍스트)은 그대로 두고 모델 내부 메모리에서 오래된 도구 응답 부분만 골라 빼는 "캐시 엔지니어링"을 제안했다. 3개 모델·4개 벤치마크 평균으로 비용은 27.7% 줄고 성공률은 1.7%p 올랐다. 이를 실제 서비스에 쓸 수 있도록 서빙 엔진 AKV도 함께 만들어 오픈소스로 공개했다.

배경: 에이전트가 오래 일할수록 '기억 비용'이 폭증한다

대규모 언어모델(LLM)은 글을 한 토큰(단어 조각)씩 생성한다. 다음 토큰을 만들 때마다 앞의 내용을 모두 다시 읽을 수는 없기 때문에, 이미 읽은 부분의 계산 결과를 저장해 두고 재사용한다. 이 저장소를 KV 캐시(Key-Value cache, 모델이 앞 내용을 '이미 읽어 둔 메모')라고 부른다.

짧은 대화에서는 문제가 되지 않는다. 하지만 AI 에이전트는 사정이 다르다. "웹에서 자료를 찾아 보고서를 써라", "이 코드 저장소의 버그를 고쳐라" 같은 일을 맡으면 검색 결과, 웹 페이지 본문, 코드 실행 결과 같은 도구 응답이 수백 회에 걸쳐 쌓인다. 다음 행동을 정할 때마다 모델은 이 거대한 메모 전체를 다시 훑어야 한다.

연구진이 측정한 결과, 이런 장기 에이전트 작업에서 KV 캐시를 읽는 비용이 전체 API 비용의 82.4%를 차지했다. 기록이 모델이 감당할 수 있는 길이(컨텍스트 창)를 넘으면 정확도가 크게 떨어지거나 실행 자체가 멈출 수도 있다.

기존 해법의 딜레마

지금까지 업계 표준은 컨텍스트 엔지니어링이었다. 대화 기록이 일정 길이(예: 9만 6천 토큰)를 넘으면 오래된 부분을 요약하거나 잘라내는 방식이다. 문제는 두 가지다.

  1. 재계산 비용: 기록 앞부분을 고치면 그 뒤의 메모(KV 캐시)가 모두 무효가 된다. 남겨 둔 기록도 처음부터 다시 읽어야 한다(이를 '재-프리필(re-prefill)'이라 한다). 앞쪽을 고칠수록 다시 계산할 양이 늘어난다.
  2. 정보 손실: 재계산 비용을 줄이려고 한계에 다다를 때까지 미뤘다가 한꺼번에 크게 요약하면, 중간 과정의 중요한 단서가 날아간다.

비유하자면, 두꺼운 업무 일지를 정리하려고 앞쪽 몇 장을 요약했더니 일지 전체를 처음부터 다시 읽어야 하는 상황이다. 그래서 정리를 최대한 미뤘다가 한 번에 대폭 요약하는데, 이번에는 필요한 내용이 빠져 버린다.

핵심 아이디어: 기록은 남기고, 메모만 덜어낸다

연구진의 제안은 단순하다. 텍스트 기록은 건드리지 않고, 모델 내부 메모(KV 캐시)에서 필요 없는 부분만 '주의(attention) 대상에서 제외'하는 것이다. 이를 캐시 엔지니어링(cache engineering)이라 부른다.

여기에는 기존의 '추가(append)' 외에 두 가지 새로운 조작이 쓰인다.

  • 드롭(drop): 선택한 부분의 메모를 이후 계산에서 빼 버린다. 나머지 메모는 그대로 재사용하므로 재계산이 필요 없다.
  • 리포지션(reposition, 위치 재조정): LLM은 각 토큰에 '몇 번째 위치인지' 정보를 붙여 둔다(위치 인코딩). 메모를 빼도 위치 번호는 계속 커지기 때문에, 메모 양이 적어도 모델의 위치 한계에 먼저 닿을 수 있다. 리포지션은 남은 메모의 위치 번호를 앞으로 당겨 붙인다. 회전 방식 위치 인코딩(RoPE)의 성질 덕분에 저장된 값을 회전만 시키면 되므로, 이 역시 다시 계산할 필요가 없다.

무엇을 뺄 것인가: 오래된 '도구 응답'

연구진은 모델이 실제로 어디에 주의를 기울이는지 관찰했다. 오래된 내용일수록, 그리고 모델 자신의 추론보다는 도구 응답(검색 결과·웹 페이지 등)일수록 덜 참고했다. 그래서 기본 정책으로 "도구 응답 롤링 드롭"을 택했다. 모델의 추론 기록은 모두 남기고, 도구 응답은 최근 12개만 유지하며 그보다 오래된 것은 차례로 빼는 방식이다.

흥미로운 점은 빼낸 메모의 정보가 완전히 사라지지는 않는다는 것이다. 남아 있는 메모(예: 모델의 추론)는 만들어질 당시 그 도구 응답을 이미 읽고 계산된 것이라, 일종의 '요약된 흔적'이 자연스럽게 남는다.

왜 새 서빙 엔진(AKV)이 필요한가

아이디어는 간단하지만 실제로 돌리기는 까다롭다. 기존 서빙 시스템은 "같은 텍스트 앞부분이면 같은 메모"라는 전제로 캐시를 재사용한다(프리픽스 캐싱). 그런데 캐시 엔지니어링에서는 같은 텍스트라도 언제 무엇을 뺐는지에 따라 메모 내용이 달라진다. A·B·C 세 문단이 있을 때, C를 읽은 뒤 A를 뺐는지, A를 먼저 빼고 C를 읽었는지에 따라 C의 메모가 다르다.

연구진은 이를 처리하는 서빙 엔진 AKV를 오픈소스 서빙 시스템 SGLang 위에 만들었다. 핵심 설계는 다음과 같다.

  • 상태 없는(stateless) 인터페이스: 개발자는 평소처럼 메시지 목록을 보내고, 어떤 메시지의 캐시를 언제 뺄지(drop)와 위치 재조정(reposition)만 옵션 필드로 추가하면 된다. 서버에 무엇이 남아 있는지 추적할 필요가 없다.
  • 확장 라디스 트리: 캐시 재사용 여부를 텍스트뿐 아니라 '드롭·리포지션 이력'까지 함께 따져서 판정한다.
  • 드롭 인지형 메모리 회수: 모든 요청이 뺀 메모는 작업이 끝나기 전이라도 GPU 메모리에서 비운다.
  • 세그먼트 배치 어텐션: 메모리가 부족해 캐시가 지워졌더라도, 복잡한 드롭 이력을 한 번의 계산으로 정확히 복원한다.

결과: 더 싸고 빨라졌고, 정확도도 소폭 올랐다

연구진은 MiniMax-M2.7, GPT-OSS-120B, MiroThinker-1.7-Mini 등 3개 모델로 4개 장기 에이전트 벤치마크를 돌렸다. 딥리서치 계열인 BrowseComp-Plus(BCP), GAIA(텍스트 103문항), xbench-DeepSearch와 소프트웨어 버그 수정 과제인 SWE-bench Verified다. 비교 대상은 두 가지다. 하나는 업계에서 흔히 쓰는 '한계 도달 시 요약' 방식(Standard, 임계값 9만 6천~19만 2천 토큰)이고, 다른 하나는 더 일찍(4만 8천 토큰) 요약하는 방식(Text Engineering)이다.

세 모델 모두에서 AKV의 평균 성공률이 가장 높았고 비용은 가장 낮았다. 전체 평균으로 Standard 대비 비용 27.7% 절감, 성공률 1.7%p 향상이다. 일찍 요약하는 방식(Text Engineering) 대비로는 비용이 21.9% 줄었다. 다만 모든 칸에서 이긴 것은 아니다. 예컨대 MiniMax-M2.7의 SWE-bench(75.2→74.4)나 GPT-OSS-120B의 xbench(38.5→37.5)에서는 성공률이 약간 낮았다.

정확도가 오른 이유도 분석했다. 기록 길이가 4만 8천 토큰 미만일 때는 세 방식의 정확도가 비슷했다. 그러나 각 요약 방식은 요약이 일어나는 지점 직후 구간에서 정확도가 가장 낮았다. 한꺼번에 크게 요약하면서 정보가 빠지기 때문으로 보인다. 반면 롤링 드롭은 오래된 도구 응답을 조금씩 빼기 때문에 이런 급락이 없다.

서빙 속도

서빙 실험은 GPT-OSS-120B 1개 모델로 SWE-bench Verified 80개 과제를 재생한 워크로드에서 진행했다. GPU 8장(NVIDIA A800) 환경에서 이 작업을 동시에 여러 개 처리하며, 각 방식이 최대 처리량을 낸 조건(AKV 동시 14개, Standard 동시 12개)끼리 비교했다. 그 결과 AKV는 Standard보다 평균 응답 지연 1.36배, 상위 5% 느린 요청(P95) 지연 1.51배 빨랐다. 출력 처리량은 1.18배였다. 동시 요청이 14개 이상으로 늘면 격차가 더 커졌다. 기존 방식은 메모리 압박 속에서 재계산이 몰리며 지연이 급증했기 때문이다(동시 16개에서 P95 지연 229.9초 vs AKV 30.6초).

부가 실험: 메모리 관리도 AI가 스스로

  • 위치 재조정의 효과: 리포지션 없이 도구 응답만 빼면 BCP 성공률은 55%였지만, 리포지션을 더하자 62%로 올랐다. 위치 번호 한계 때문에 중간에 멈추던 탐색을 계속할 수 있었기 때문이다.
  • 무엇을 뺄지가 중요: 모델의 추론 기록을 빼면 도구 응답만 뺄 때보다 성공률이 낮았다. 에이전트에게 '생각의 흐름'이 더 중요하다는 뜻이다.
  • 재귀적 자기개선(RSI): MiniMax-M2.7에게 캐시 정책을 스스로 고쳐 나가게 했더니(20개 과제로 개선, 별도 100개 과제로 평가), 사람이 설계한 정책보다 비용을 7.1% 더 줄이면서 정확도를 유지하는 정책을 찾아냈다.
  • 도구로서의 캐시 관리: 캐시 정리 기능을 에이전트가 직접 호출하는 '도구'로 주자, 두 모델 모두 BCP 일부 과제에서 성공률이 가장 높았다(GPT-OSS-120B 61.0%, MiniMax-M2.7 64.0%). 다만 MiniMax-M2.7은 더 오래 탐색하면서 비용이 오히려 늘었다(5.4→5.9센트).

의미: '무엇을 기억할지'를 텍스트가 아닌 메모리 수준에서 결정

이 연구의 의미는 에이전트의 기억 관리 단위를 바꿨다는 데 있다. 지금까지 '컨텍스트 엔지니어링'은 프롬프트와 대화 기록이라는 텍스트를 다듬는 기술이었다. 캐시 엔지니어링은 같은 목표를 모델 내부 메모리 수준에서 달성한다. 그래서 재계산 비용과 정보 손실 사이에서 양자택일할 필요가 줄어든다.

실용적인 파급력도 있다. 에이전트 서비스 비용의 대부분이 캐시 읽기라는 점을 생각하면, 정확도를 떨어뜨리지 않고 비용을 4분의 1가량 줄이는 것은 운영자 입장에서 큰 차이다. 기존 API와 호환되는 상태 없는 인터페이스를 택했기 때문에, 개발자가 요청에 필드 몇 개만 추가하면 된다는 점도 도입 장벽을 낮춘다.

한계와 향후 과제

  • 동료 심사 전 프리프린트: 2026년 10월 20일 arXiv에 공개된 논문으로, 아직 학회 심사를 거치지 않았다. 모든 수치는 연구진의 자체 측정이다.
  • 비용은 계산값: '비용'은 실제 청구액이 아니라, 소비 토큰에 공개 API 단가(Groq, MiniMax 공식 단가 등)를 곱한 추정치다. 연구진은 위치 재조정 비용을 일부러 높게 잡았다고 밝혔지만, 실제 상용 API의 캐시 요금 구조에 따라 절감 폭은 달라질 수 있다.
  • 평가 범위: 모델 3종과 4개 벤치마크에서 검증했다. 일부 실험(소거 실험, RSI, 도구형 관리)은 100개 이하 과제 규모로, 결과 차이가 몇 %p 수준이라 통계적 변동 가능성을 감안해야 한다. 벤치마크별로는 성공률이 기존 방식보다 낮은 경우도 있었다.
  • 하드웨어 조건: 서빙 실험은 단일 모델·단일 워크로드(GPT-OSS-120B, SWE-bench Verified)를 A800 GPU에서 모델 가중치를 BF16으로 돌린 결과다. 다른 하드웨어나 양자화 환경에서는 수치가 다를 수 있다.
  • 상용 API에는 아직 적용 불가: 캐시 엔지니어링은 서버가 KV 캐시 조작을 지원해야 한다. OpenAI·Anthropic 같은 폐쇄형 API 사용자는 제공사가 기능을 열어 주기 전까지 쓸 수 없다. 자체 서빙하는 오픈 모델에 먼저 적용될 가능성이 크다.
  • 연구진이 밝힌 과제: 더 다양한 캐시 정책 탐색, 캐시 엔지니어링을 전제로 한 에이전트 학습, 선형 어텐션 계열 모델로의 확장은 향후 과제로 남았다.
